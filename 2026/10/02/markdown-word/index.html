Designing a Markdown-to-Word Converter: Structure, Styles, and Lost Formatting

Published2026-10-02|Updated2026-10-02|Engineering Lessons

Designing a Markdown-to-Word Converter: Structure, Styles, and Lost Formatting

把 Markdown 转成 Word，很容易从一个简单需求开始：标题套上字号，正文加首行缩进，再放一个页码。真正遇到长文时，问题会落到结构上：一个段落里的粗体还在不在？标题只是看起来大，还是具有 Word 的标题语义？输入中的数字方括号究竟是文献标记，还是普通数据？

我的 md2docx 工具 采用 JavaScript 和 docx 库，把一个有限 Markdown 子集转换为中文文档。本文以公开提交 3448b828a5 为分析对象，核验于 2026-10-02。重新检查代码时，我发现正文处理顺序会先删除粗体、斜体标记，再尝试识别它们。这个小问题正好说明：转换器需要先保存语义，再处理外观。

首先声明输入语言的范围

“支持 Markdown”是很大的承诺。CommonMark 包括块结构、行内结构与很多边界规则，常见平台还会增加表格、删除线和其他扩展。项目当前的块解析器主要识别三级 ATX 标题、普通段落、空行与分隔线，没有实现完整列表、表格、代码块、图片、链接与数学公式的语法树。

这个范围对于受控的小型写作流程可以有用，前提是把它明确告诉作者。否则，一份包含围栏代码块或多级列表的输入可能被当作普通段落输出，文件能打开，内容结构却已经变了。程序没有抛出异常，不等于转换保持了作者的意图。

我会把输入约定写成一份小规格：允许哪些块、是否支持嵌套、换行如何处理、数字引用如何识别，以及遇到不支持语法时如何报告。可以选择拒绝、警告或按普通文本保留，但每种行为都应稳定，不能随某条正则意外变化。

需要扩大语法范围时，采用成熟解析器得到 AST，往往比继续叠加字符串替换更容易维护。CommonMark 规范 可以帮助构造边界样例；这里不要求小工具立刻完整实现它，而是用它界定“当前子集”与“完整 Markdown”的距离。

内容、语义和排版最好分三步

原始文本是输入，段落、标题、强调、引用等是结构，字号、缩进和字体则是排版策略。若在第一步就把星号、括号和换行全部删除，后面就只能依赖猜测恢复结构。

一个更清晰的处理过程可以是：

Markdown 文本
  → 块节点：标题、段落、列表、代码……
  → 行内节点：普通文字、强调、链接、引用……
  → 文档中间表示
  → Word 段落、TextRun、样式与节属性
  → docx 文件

中间表示不一定复杂。对当前工具而言，标题层级、段落内若干文本 run，以及引用标记类型，已经足够把解析与 Word 生成拆开。以后换成另一套文档库或输出 HTML 时，解析层就不必跟着重写。

结构层还应保留原文位置。转换失败时，告诉作者“第 38 行表格暂不支持”，比生成一个几乎正确但无法定位问题的 Word 文档更有用。源位置也能帮助测试把输出异常追溯到具体输入。

一次粗体丢失是怎样发生的

当前代码已经有一个 parseInline 函数，能够识别星号强调和数字引用。但构造普通段落时，它先调用 stripMarkdown，把粗体与斜体的标记清掉，再将结果传给 parseInline。因此行内解析器拿到的已经是纯文本，无法知道哪些字原来需要加粗。

可以用三个阶段观察这个问题：

输入：       这里有 **重要术语** 和 *补充说明*。
提前清理：   这里有 重要术语 和 补充说明。
行内解析：   所有内容都只能识别为普通文字。

这个例子没有涉及 Word 渲染器，单纯从数据流就能定位原因。README 列出“支持粗体、斜体”，函数也看起来支持，仍然不足以证明整条调用路径保存了格式。能力描述应该依据实际入口到输出的行为。

合理的修正方向是让普通段落直接进入行内解析，再把各 run 的属性交给文档构造层。标题如果希望统一加粗，可以单独定义标题的行内语义策略，不能因此让正文复用一个破坏信息的清理过程。本文只对公开版本做分析，没有把建议描述成已合并到工具仓库的修复。

还需要考虑嵌套和转义。只用一个简单正则处理 ***组合强调***、字面星号或跨行内容，很容易得到不符合预期的结果。若输入限定为简单强调，测试就应验证这个限定；一旦要支持复杂嵌套，保留 AST 会比继续调整正则优先级更清楚。

Word 标题语义与视觉样式

标题不能只靠“大一点、粗一点”。具有正确 heading level 的段落，可以参与导航窗格、目录生成和结构化编辑。项目构造标题段落时使用 HeadingLevel，并设置对应段落样式，这比只修改 TextRun 字号更接近可持续编辑的文档。

样式名称、层级和直接格式之间仍有关系。若每个段落都写入大量直接格式，后来在 Word 里修改统一样式时，部分属性可能继续被覆盖。模板化文档适合尽量让样式承担共同规则，仅对少数局部内容施加直接格式。

标题与普通正文的缩进、段前段后、分页行为也应分别考虑。一个一级标题独自落在页尾，下一页才出现正文，即使字号符合要求，阅读体验仍然不好。标题保留与下一段同页、孤行控制等行为，需要在目标渲染器中观察，不能只检查 XML 字段是否存在。

这里最好维护一份视觉样张：连续标题、标题后短段、跨页长段、含英文术语的中文段落以及多级结构。它比用一页全是短句的测试材料更容易发现分页与样式冲突。

字体与单位不能只看注释

文档库使用的单位未必是用户界面里的 pt 或厘米。项目的字号配置使用半磅值，例如 24 对应 12pt；页边距与部分缩进参数采用文档单位。正确的转换需要依据所用库版本与生成的 WordprocessingML 核验，不能看到数字 24 就直接说是 24pt。

首行缩进尤其容易产生误解。当前配置写入的是一个固定距离，并在注释里称为“两字符”。固定距离不总能等于当前字体与字号下的两个汉字宽度；当正文样式改变时，这种近似可能失效。若要求严格按字符计算，应使用相应字符单位表达或核对生成结果。

中英文字体也是多语言排版问题。为一个 run 设置字体名称，并不保证所有脚本和回退场景都严格使用预想字体。当前代码主要把数字引用设成 Times New Roman，普通文字则采用中文字体配置；它没有按字符范围把所有英文术语单独切成英文 run，因此 README 中“双字体”的描述应理解为当前规则的有限覆盖。

另一台机器若没有安装字体，渲染器会替换，换行和页数也可能改变。交付需要同时说明字体环境与可接受的替代方式。文件可编辑与视觉完全一致是不同目标，必须按用途决定验收优先级。

数字方括号不一定是文献

项目把类似 [1]、[2][3]、[1-3] 的模式转成上标。这个规则对受控论文正文很方便，但纯靠词法形状无法判断含义：数组元素、题号、日志片段和 Markdown 链接标签也可能使用方括号。

如果作者要写普通文本“读取数组 [1]”，转换器不应悄悄把它变成文献引用。加入代码语义之后，引用识别就可以明确排除 code span；如果采用结构化引用语法，还可以区分文献键与显示编号。关键是先找到语义归属，再决定上标样式。

引用格式和文献真实性也要分开。把 [7] 排成上标，只完成外观转换，没有验证第七条文献是否存在、作者顺序是否正确，也没有维护交叉引用更新。静态数字可以满足简单稿件，但长文若频繁插入或删除文献，就需要引用系统或明确的编号检查。

比较实用的验证方式是，收集正文使用的引用标识与参考文献条目，检查缺失和未使用项，再由独立步骤核对文献来源。不要让排版工具的成功消息替代内容审校。

为什么不能把换行都当空格

Markdown 的软换行、硬换行和段落边界具有不同语义。当前块解析器把连续非空行合为一个段落并保留换行字符，具体显示效果还取决于文档生成层怎样处理这些字符。若希望得到显式换行，应构造对应的文档元素；若只是源文件为了可读性而折行，则通常不希望每行都强制换行。

代码、地址、诗歌和公式推导又有各自需求。把所有输入统一压成段落，可能改变原本依赖布局表达的含义。更稳妥的方法是由块节点决定空白策略：普通段落处理软换行，代码块保留空格与行号含义，列表保持项目边界。

输出中的表格也不能靠空格对齐。字体与页面宽度变化后，文本空格很难维持列关系；真正的 Word 表格需要行、列与单元格结构。当前工具没有这部分能力，就应直接提示，而不是把一段管道字符当成已经转换好的表格。

转换器测试可以分成三层

第一层只测试解析：给定固定输入，得到哪些块和行内节点。这里不需要打开 Word，测试速度快，也容易覆盖转义、空行、强调和数字标记。前面的格式丢失问题，就可以用“输入强调最终仍有 bold run”这个断言暴露。

第二层检查生成结构：把 docx 当作包含 XML 的容器，检查标题层级、段落属性、run 文本、页眉页脚和必要关系。结构检查能够回答“是否真的生成了标题样式”“有没有丢字”，但对页面如何排版仍然无能为力。

第三层才是渲染验收：在指定 Word 或兼容渲染器中打开，检查分页、字体替换、表格溢出、公式位置和页眉覆盖。这个阶段应保存环境信息与代表性预览。不同渲染器之间出现差异时，先确定目标交付环境，避免无穷地追逐像素一致。

测试样本不需要很长，但应故意覆盖冲突：包含星号的普通文字、带数字的代码、中文与英文相邻、紧邻标题的引用、跨页长段。一个全部由普通段落组成的长文，只能反复验证已经简单的路径。

文件输出也需要失败语义

内容转换成功之后，还有写入阶段。输出路径应避免意外覆盖输入，扩展名推导也要检查边界：没有 .md 后缀的输入，不能因为简单替换没有命中，就得到与输入相同的默认目标。写入前确认两个路径不同，是独立于格式正确性的保护。

更稳定的流程是先在目标目录写临时文件，确认打包成功后再原子替换最终输出，并在失败时返回非零退出码。若存在已有文件，是否覆盖应由明确参数或调用方策略决定，不能让批量任务默默改掉先前结果。

项目当前的 Promise 写入链比较简洁，后续可以补充异常处理、源目标冲突检查和写入后的结构验证。它们不会让文档看起来更漂亮，却能让工具在自动化流程里可靠地报告“完成”或“失败”。

用一份小样本验收一次模板变更

假设模板升级只调整正文样式，可以准备一份固定输入：两个标题、一段含 **加粗** 与 *斜体* 的正文、一个普通数字标记、一处代码中的方括号，以及足以跨页的长段落。先给每种语义写出预期，再比较新旧输出；不要先看新文件是否漂亮，最后才想起检查内容有没有少。

内容层可以提取文档中的文本 run，按段落顺序比较。强调标记在源文件中消失是预期，但强调内部的字不能丢；代码中的星号可能是字面内容，也不能统一删除。只比较去除全部标点后的纯文本，会掩盖这些差异，因此要按输入节点的语义确定比较方式。

结构层检查标题级别与强调属性，区分样式引用和直接格式。视觉层再观察跨页处：标题是否孤悬在页尾，正文首行缩进是否仍合适，页眉有没有覆盖内容。若字体替换导致页数改变，应保留环境差异，不能仅凭页数不一致判定转换失败。

最后把生成器版本、依赖锁文件、模板配置与样本输出关联起来。模板修改后，重跑的是同一组语义样本，新增功能则补充对应反例。这样下次收到“新版加粗没了”的反馈，就能判断问题来自解析、样式还是渲染环境，而不是在一份复杂稿件里逐段猜测。

这组步骤是后续完善工具的验收建议，不代表当前仓库已实现自动回归。它也不需要每次处理用户完整论文：小样本先发现规则冲突，真实稿件再验证覆盖不足的内容，两者承担不同任务。

一套可维护的模板应怎样保存

我会把文档转换器交付为四部分：输入语法约定、样式配置、转换实现和验收样本。模板修改先作用于统一配置，再用同一组样本检查结构与渲染，避免每次文档都临时补丁式调整。

对当前项目，可以先修复正文强调的数据流，再为未支持语法增加可见警告，最后逐步引入结构化解析。这样的顺序保留了小工具的简单性，同时把功能承诺拉回可验证的范围。工具依赖的 API 应以 docx 官方文档 与锁定版本为准。

这次复盘使我更看重转换链里的信息保存：标题层级、强调、引用和空白都应在合适的阶段处理。只要前面没有丢掉语义，后面就可以换模板、换字体、换渲染器；若过早把它们清成纯文本，再精细的排版参数也无法可靠恢复作者原本的意思。
