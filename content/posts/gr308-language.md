# GR308 语言模型调优复盘：并行拓扑、MTP、Graph 与真实验收

同样是把模型放到 GR308 上，9B 模型适合把两个逻辑芯片拆成独立副本，30B MoE 在测试中关闭专家并行反而更快，80B 模型则需要四路张量并行。27B 的一次大幅加速，后来又被冷启动对照修正了归因。调优最有价值的部分，正是这些选择怎样被实验逐步筛出来。

本文整理 2026 年 9 月的本地报告、指标 CSV 与对应 Codex 工作区记录。10 月 2 日进行的是证据整理，没有重新运行设备实验。型号沿用各报告的模型标识；不同 checkpoint、驱动、容器与请求长度各自成组，不把它们拼成硬件排行榜。多模态分支另见 [Qwen Image 实现复盘](/2026/10/02/gr308-image/) 和 [Wan / H3 报告](/2026/10/02/gr308-video/)。

## 先定义一张卡、一个副本与一个成绩

这些实验中的 GR308 物理卡包含两个逻辑设备。TP2 表示一个模型被切到两个逻辑设备，并不自动表示用了两张物理卡；具体放置还要看实验记录。DP2 则是两份独立模型副本，各自接受请求。9B 的 TP1+DP2 和 30B 的 TP2 都可以占用一张双芯物理卡，但通信行为完全不同。

TP 会切分一层的权重或中间表示，再通过集合通信汇总结果；副本并行直接分发不同请求，在副本之间通常不需要逐层汇总。选择的第一步是看模型能否单芯装下，其次才是单请求延迟、总吞吐和显存余量。不能因为 MoE 有很多专家，就默认增加 EP 一定有效：专家派发引入的数据搬运、负载不均与实现开销也会进入关键路径。

表中的 aggregate output tok/s 是整个测试窗口内的输出吞吐；Decode tok/s 是报告按平均 TPOT 换算的单请求解码速度。两者分母不同。TTFT 包括首个输出前的等待与计算，不能只当 prefill kernel 耗时。并发增加以后，总吞吐上升而每个用户的输出速度下降，可以同时发生。

9 月 17 日四模型报告主要使用 vLLM 0.18.0、vllm_fant 1.1.0.20 与 BF16。9B、30B、35B 请求为 3072→1024 tokens；80B 为 1024→1024。下表没有混入报告中的外部参考成绩。

| 模型与选中路径 | C1 总输出 tok/s | C16 总输出 tok/s | C16 TTFT / 平均 TPOT | 证据范围 |
| --- | ---: | ---: | --- | --- |
| Qwen3.5-9B，TP1+DP2，MTP4 | 48.62 | 247.16 | 3501.62 / 52.90 ms | C1、C16 各 64 请求，均零失败，正式测试 |
| Qwen3-30B-A3B，TP2，无 EP / MTP | 25.76 | 225.67 | 4225.69 / 65.69 ms | C1、C16 各 64 请求，均零失败，正式测试 |
| Qwen3.6-35B-A3B，TP2，MTP4 | 47.21 | 180.64 | 3321.47 / 71.76 ms | C1 16、C16 32 请求，短测候选 |
| Qwen3-Next-80B-A3B-Instruct，TP4，MTP3 | 47.13 | 255.93 | 3535.56 / 50.74 ms | C1 16、C16 32 请求，短测候选；两张物理卡 |

30B 的 C32 为 320.90 tok/s，35B 的 C32 为 208.08 tok/s，各 64 请求，但原始 CSV 仍标记为 short。请求数相同也不能自动升级为多轮正式验收：实验类别、重复次数和工作负载覆盖还需要一起看。

## 9B：先改变部署单位，再调整草稿长度

9B 的主要收益来自把 TP2 改为同一物理卡上的两个 TP1 副本。短测中，C16 总吞吐从 157.67 升到 247.87 tok/s，约增加 57%。单芯能够容纳模型后，去掉逐层跨芯通信，比先写一个更复杂的算子更有效。最终正式值是 247.16，文章保留正式值，不把短测最高点当最终交付。

随后才调整 MTP。它让模型先提出若干候选 token，再由主路径验证，以增加一次验证后可提交的 token 数。MTP1→MTP3 的某组 C16 对照从 205.71 升到 231.81；最终候选采用 MTP4。这里不能把每个局部增益相乘，因为它们的其他参数与基线可能已经不同。

调度预算也有影响。`max_num_batched_tokens` 从 2048 增到 4096 后，相关对照从约 215.8 升至 237–239 tok/s。更大预算减少了部分工作被切碎的机会，却可能提高临时内存和首 token 等待，因此后续仍需检查 TTFT。最终采用 Graph 捕获尺寸 [4,8,16,32]、block size 800、自动 KV 预算和同步调度。扩大 Graph 到 64 没有形成稳定收益，自动 KV 的局部容量收益也只有约 0.9%。

这个项目实际采用了三个层次的技术：部署副本消除不必要的通信，MTP 减少逐 token 验证开销，调度和 Graph 控制发射粒度。收益主次要按实验排列，不能把最后留下的所有开关都写成同等重要。

## 30B MoE：专家并行不等于默认更快

30B 的选中配置是 TP2、不启用 EP、MoE 后端 auto、Graph [4,8,16,32]、batch token 4096、block size 800、固定 8 GiB KV，并启用异步调度。模型名字里的 A3B 说明每 token 激活参数较少，但全部专家权重仍要被存储、分片和访问。

EP2 在 C16 / C32 的结果分别为 185.86 / 230.52 tok/s，低于最后保留的无 EP 路径。减少一部分本地专家工作不一定抵消 token 派发和汇总成本。能够证明的是这组拓扑和实现没有赢，尚不足以断定硬件上的所有专家并行都无效。

一次 grouped Triton 候选得到 321.35，对照为 320.90，只差约 0.14%。如此小的差值不足以支撑额外维护一条默认路径。把 batch token 提到 6144，也只换来约 0.8% / 0.2% 的吞吐变化，却让 TTFT 增加约 30%–47%。如果只按最终 tokens/s 排名，这种候选容易被误选。

自动 KV 在 C16 略好、C32 反而变差，最终仍保留固定预算。该分支说明，调度参数要对服务目标负责：有的参数改善短时吞吐，有的扩大可容纳请求数，还有的只是改变排队位置。它们并不都意味着模型计算更快。

## 35B 与 80B：MTP 有效，但不能跨模型照搬

35B 的最终短测路径是 TP2、MTP4、Graph [4,8,16,32,64]、batch token 4096、block size 1088、自动 KV、同步调度。在 batch token 2048 时，MTP3→4 让 C16 从 164.38 升到 175.57；随后把预算改到 4096，得到 180.64，同时 TTFT 从 5593.57 降到 3321.47 ms。

继续加参数并没有持续进步。Graph128 只有约 0.5% 的变化；batch6144 的吞吐变化在负 0.5% 到正 0.48% 附近，且 TTFT 变差。Triton fused 路径 C16 / C32 为 167.69 / 188.63；EP2 linear 为 167.81 / 185.50，都没有超过选中路径。一个 round-robin 配置实际静默回退到了 linear，这不是合法的策略 A/B。C64 还遇到 SSM state indices 非连续的问题，因此不提供稳定 C64 成绩。

80B 使用 TP4，分布在两张物理卡。无 MTP、MTP1、MTP2、MTP3 的 C16 结果依次是 177.71、231.30、251.49、255.93 tok/s。MTP3 相对 MTP2 的总吞吐提升不大，但 C1 从 36.75 升到 47.13，因此最终选 MTP3。这里同时观察了吞吐与低并发体验。

其余参数是 Graph [4,8,16,32,64]、batch token 2048、block size 1088、固定 8 GiB KV 和同步调度。EP4 只得到 233.93，TTFT 还增加约 21.2%。TP2+DP2+EP 的尝试先碰到设备类型被写为 CUDA 的兼容问题，修过 CPU 设备处理后又遇到固件 semaphore/profile 失败，不能列为可用方案。

80B 的 255.93 是整条 TP4 路径总吞吐。除以两张物理卡可得到 127.97 tok/s/卡的折算指标，但它不是在单卡上独立运行得到的成绩。类似换算只适合成本记账，不能替代另一种拓扑的实验。

## 27B：一次冷启动复测改变了结论

27B 材料必须按时间阅读。9 月 11 日报告中的 BF16 基线是四张物理卡、八个逻辑设备、四个 TP2 副本，每副本 C16，合计 C64，3072→1024 tokens。KV block 从 144 调到 152 后，总吞吐 46.455→72.781 tok/s，抢占次数 144→0。这个变化确实说明旧配置存在容量问题。

当时 BF16 每副本约 18.195–18.267，FP16 单副本两次为 19.0828、19.0729，平均 19.0779，约快 4.5%。但四副本 76.312 只是据此计算的投影，没完成对应整机实测；FP16 的材料也不足以声明业务质量验收通过。slab8 在短 decode 看起来增加约 18.9%，长请求却只有 17.9539，说明局部计时会改变候选排序。

9 月 14 日的受控对照使用同一 TP2、BF16、C16、64 请求、3072→1024。厂商配置的无投机基线已经是 53.574 tok/s；把 KV 设为 152 得到 53.587，只差 0.023%。因此，后来约 18→53 的差距不能继续归因于 KV block。移除厂商配置还会在启动时申请 512 MiB 失败，尽管监控显示仍有较多空闲显存；该事实证明环境相关，不足以独自定位分配器根因。

MTP1 的历史成功也要保留前置状态：51.52→67.75 tok/s 的那次 C16 测试，发生在同进程先完成 C1×64、运行约 3596.9 秒之后。新进程直接做 MTP1+Graph32 的冷 C16，两次都在完成边界卡住，接受率从约 90%–96% 降到零，仍有 16 个 running 请求，并出现共享内存广播超时。

| 27B 观察 | 可以得出的结论 | 尚不能得出的结论 |
| --- | --- | --- |
| 无投机受控基线约 53.6 tok/s | 旧低基线不再适合作为当前 MTP 对照 | 所有差值都来自某一个开关 |
| 暖进程 MTP1 51.52→67.75 | 该运行状态下曾获得约 31.5% 吞吐收益 | 冷启动 C16 稳定可部署 |
| C1 6.14→18.22，TPOT 173.8→49.28 ms | 投机在低并发有较大潜力 | C16/C64 同比例受益 |
| C16 TTFT 14.61→18.49 s | 收益同时带来首 token 代价 | 单个吞吐数字覆盖全部体验 |
| MTP3 C16 35.44，平均接受长度 1.038 | 草稿加长的验证成本未被接受收益抵消 | MTP 深度越大越快 |

这一分支最终应写成“获得候选收益并发现冷启动稳定性问题”。把 67.75 直接乘四写成已交付整机吞吐，会同时忽略副本互扰与冷启动失败。工作区里的后续对照，比早期汇报中醒目的最高值更重要。

## DeepSeek、GPTQ 和尚未完成的模型分支

DeepSeek-R1-Distill-Qwen-7B 的第三方报告复核位于 H3 工作树中，主目录索引不显眼。条件是 FP16、TP1、一个逻辑芯片，1024→1024、C8、8 个请求、忽略 EOS、temperature 0。第三方 PDF 的 205.11 tok/s 缺少三份原始 CSV，不能当作本次复现成功。

旧 1.1.0.17 镜像在当时 1.1.0.19 驱动下卡在 KV 初始化。改用 1.1.0.20 后，eager 得到 33.68，Graph8 得到 33.89 tok/s；各完成 8/8。Graph 的增幅约 0.62%，TTFT 3.221→2.562 秒，平均 TPOT 234.64→233.55 ms。每种模式只有一次正式运行，这是一份兼容性与复现差异记录，还不能宣布设备性能上限。

9 月 7 日交接中的 Qwen3.8-27B GPTQ 也必须区分存储、计算与质量。INT4 权重由 INT32 容器打包，实际激活/矩阵路径要求 FP16，部分内部状态仍是 FP32；TP 通信随激活走 FP16。接口可以接收请求，不代表量化实现合格。早期 200 题中，BF16 为 127/200，GPTQ 为 0/200，输出退化为重复符号；真实 packed 层还出现大幅数值偏差。较晚的精度调查确认 HTTP 请求能完成，但没有补出替代这份质量失败的完整验收，因此不能把“最低可启动精度”写成“最低合格部署精度”。

## 最后交付的应当是可解释的配置

这批实验的实现过程有一条清楚的顺序：先核对逻辑设备和物理拓扑，再建立固定请求基线，接着比较 TP/DP/EP，最后才调 MTP、Graph、KV 与 token budget。每轮把启动、实际分发后端、完成数、错误、TTFT、TPOT 和总吞吐一起保存，才能发现“配置写了但没有生效”以及“短测成功但冷启动卡住”。

明确保留的成果包括 9B、30B 的正式 C1/C16 配置，35B、80B 的短测最优候选，以及 27B 的基线修正和稳定性边界。失败分支同样减少了后续搜索空间：EP 并不默认更优，草稿长度不能无限增加，单算子或短 decode 的收益也不能替代真实服务请求。

本文的本地证据包括《风华 GR308 Qwen 系列调优结果总结》（2026-09-17）及 `final_metrics.csv`、《Qwen3.6-27B vLLM 调优总结》（09-11）、《Qwen36 C16 Controlled A/B》（09-14）、《GR308 测试交接文档》（09-07）、H3 工作树中的第三方报告复核（09-10），以及对应工作区后续记录。数值是历史实验结果，本轮没有重新认证当前服务器状态。通用的实验设计方法另见 [推理优化怎样形成可信结论](/2026/10/02/inference-evidence/)。

## 复核配置时，保留失败路径的作用

这次整理没有把最后一份报告覆盖掉前面的所有记录。对同一个模型，旧结果仍然解释了为什么会尝试某个方向：早期抢占推动了 KV 容量调整，短 decode 的正结果推动了更长请求的复测，暖进程成功又推动了冷启动对照。后续证据改变的是当前结论，不应抹去实验的因果顺序。

例如，模型名称本身并不能解释哪一步在等待；这里真正有解释力的是相同请求下的抢占计数、接受长度、已完成请求数和错误位置。一个候选若只在稳态有效，启动过程就应成为单独验收项；一个候选若在高并发卡住，低并发成功也不能替它签署容量承诺。

更具体地说，MTP 的成本至少包含提出候选、验证候选以及维护状态。接受率高可能减少主模型重复轮次，但如果一次验证扩大了工作量、增加缓冲区或引入额外同步，最终吞吐仍可能下降。材料中 MTP3 的低平均接受长度与退化相互呼应；它提供的是该配置不值得保留的证据，而不是对全部投机解码的否定。

Graph 也必须检查实际捕获与命中。不同 batch bucket 占用额外内存，不能只在命令里添加更大的尺寸就认为所有请求都会更快。状态索引不连续、后端静默回退或启动申请失败，会让一个表面相同的配置走到不同执行路径。文章保留这些失败，是为了让后来读者知道应该在哪里确认真实行为。

最终，配置记录应与模型修订、软件栈、请求长度和测量窗口共同保存。只留下启动参数，无法解释某个开关为何被选中；只留下最高吞吐，无法知道付出了多少首 token 延迟或稳定性代价。本文的表格与失败矩阵正是同一份结果的两面，后续新增实验也应沿这些条件更新。

相关 GRServe 工作区另有“可移植核心与 Fant 首个后端”的设计规格，讨论 Backend ABI、能力协商、执行计划、兼容与原生两条路径。这一部分目前属于设计证据，不能把计划中的 KV、TP、Graph 或跨厂商性能目标算进上述已经取得的模型结果。后续若形成真实实现和同口径验收，应以独立工程文章记录，而不是借用现有 vLLM 基线替它证明完成。
