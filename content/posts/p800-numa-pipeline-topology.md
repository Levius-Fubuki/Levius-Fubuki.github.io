# 从 NUMA 到流水线：P800 三机部署 Kimi-K3 的拓扑与瓶颈笔记

这次排查从两个看似简单的问题开始：一台 P800 服务器里的卡是不是都通过 PCIe 通信？如果三台机器的加速器活动率差别很大，是不是模型层分配错了？

把设备拓扑、CPU/NUMA 归属和推理时间线放到一起后，我发现，这两个问题都不能只靠一张利用率截图回答。机内有专用的 XPULink，也有 PCIe 和跨 NUMA 路径；模型层数可以平均，等待方式却可能完全不同。

这篇笔记记录三台八卡 P800 运行 Kimi-K3 的结构，以及从已有实验中能得出什么、还不能得出什么。硬件核查时间是 2026 年 10 月 14 日；性能数字来自 10 月 13 日不同阶段的诊断与短测。2026 年 10 月 18 日补充了 10 月 16 日 Eagle3 全量验证的修复、验收与恢复结果。为了保留工程关系而不暴露访问地址，文中使用节点 53、55、57 作为服务器编号。

## 一、先认识 P800：软件接口与实际硬件要分开看

P800 是昆仑芯的 AI 加速器，采用 XPU-P 架构。官方介绍中的 P800 OAM 模组依据 OCP-OAM 标准设计，支持通过 IB 或 RoCE 构建集群。这里讨论的是现场三台服务器的实际连接关系，而不是把厂商宣传中的某种超节点配置直接套进来。[架构介绍](https://www.kunlunxin.com/news/4720.html)、[OAM 与互连介绍](https://www.kunlunxin.com/news/4791.html)。

现场每台有八张 P800，每卡显存 96 GiB。使用中的软件栈包含 vLLM、昆仑插件、XPU SDK 和 BKCL 通信库。环境里能看到 `nvidia-smi`、`torch.cuda`、CUDA 风格的 stream 和 graph 接口，但这些接口名字不能作为 NVIDIA GPU 或 NVLink 硬件的证明。分析性能时，要沿着实际加载的昆仑实现追踪。

这也解释了为什么排查时必须核对运行路径：改了工作区代码，不代表安装包中的插件已经更新。之前一次“四补丁评估”就因为改动没有进入实际执行路径而撤回。随后 P1 补丁才在真正加载的安装包中完成验证。

## 三、2 sockets、8 NUMA，为什么图中曾经只有四个分支？

一台服务器有两颗物理 CPU，也就是 **2 sockets**。三台都是双路 Hygon C86 P455，每颗 64 核、128 线程，整机合计 128 核、256 线程。

NUMA 不是 CPU 插槽的另一种叫法。它是操作系统描述 CPU 核和内存就近关系的局部域。同一颗物理 CPU 可以划分成多个 NUMA 节点。

实际 `lscpu` 映射确认：

- socket 0 包含 NUMA 0、1、2、3。
- socket 1 包含 NUMA 4、5、6、7。
- 每个 NUMA 都有 16 核、32 线程及对应的主机内存。

之前只画了 P800 和 400G 网卡所在的 NUMA 1、3、5、7，所以看起来像整机只有四个 NUMA。完整图补齐了其他四个节点，并加入 NUMA 0 上的管理网卡 eth0。

| NUMA | Socket | CPU 逻辑编号 | 主机 RAM，约 GiB | 本图涉及的设备 |
|---:|---:|---|---:|---|
| 0 | 0 | 0–15, 128–143 | 187.9 | eth0，100G |
| 1 | 0 | 16–31, 144–159 | 188.5 | XPU0/1、eth1 |
| 2 | 0 | 32–47, 160–175 | 188.5 | CPU / 主机内存 |
| 3 | 0 | 48–63, 176–191 | 188.5 | XPU2/3、eth2 |
| 4 | 1 | 64–79, 192–207 | 188.5 | CPU / 主机内存 |
| 5 | 1 | 80–95, 208–223 | 188.5 | XPU4/5、eth3 |
| 6 | 1 | 96–111, 224–239 | 188.5 | CPU / 主机内存 |
| 7 | 1 | 112–127, 240–255 | 184.5 | XPU6/7、eth4 |

表中的逻辑 CPU 编号包含 SMT 线程，不能把 32 个逻辑编号读成 32 个物理核。

### 相对距离描述什么？

以 NUMA 4 为例，到 NUMA 0–7 的距离为：

```text
目标节点：  0   1   2   3   4   5   6   7
相对距离： 25  27  27  27  10  15  15  15
```

从 NUMA 4 的 CPU 核出发，访问本节点内存的距离是 10；访问同一颗 CPU 内其他节点的内存是 15；跨到另一颗 CPU 是 25 或 27。

这些数值是固件报告的相对访问距离。它们不是纳秒、带宽，也不能说明实际延迟就是本地访问的 2.7 倍。它们描述的是 CPU 与主机内存的关系，不是 P800 的 XPULink 速度。

### MemTotal 与显存为什么必须分开？

NUMA 的 `MemTotal` 是操作系统报告的主机 RAM 总容量，不是当前剩余可用内存，也不是加速器显存。OS 管理的容量可能略少于内存条的标称容量。

例如 NUMA 5 有约 188.5 GiB 主机 RAM，附近的 XPU4、XPU5 又各有 96 GiB 显存。这些是不同的内存资源。模型加载通常涉及主机到设备的数据传输，设备计算主要使用卡上的显存，不能把这些数字直接当作一块统一的高速内存池。

### NUMA 2、4、6 是否没用到？

没有挂接本图中的 P800 或 400G 网卡，不等于没有工作。它们仍可运行分词、请求调度、模型加载、后台进程，也可承载主机内存分配。

如果没有限制线程与内存归属，Linux 可能使用这些节点。它们在某次推理中到底用了多少，要看 worker 绑定、线程位置和 `numa_maps`。对性能更有意义的问题是：频繁与 P800 交换数据的 CPU 线程和缓冲区，是否靠近对应的加速器？

## 四、卡间是不是都走 PCIe？

三台卡间矩阵一致，机内存在两类需要区分的连接：

1. **XPULink 路径。** XPU0–3 组内全连接，XPU4–7 组内全连接，跨组还有 0↔4、1↔5、2↔6、3↔7。
2. **PCIe / NUMA 路径。** 工具将其余部分卡对报告为 SYS；GPU 与近端网卡之间则报告 PIX。

八卡共有 16 个 XL 卡对，每卡四个 XL 邻居；其他 12 个卡对报告 SYS。

| 标签 | 工具报告的含义 |
|---|---|
| XL | 路径经过 XPULink |
| PIX | 路径至多经过一个 PCIe bridge |
| SYS | 路径经过 PCIe 与跨 NUMA 的 CPU 互连 |

这个矩阵告诉我们设备的连接条件，却不能直接告诉我们 BKCL 一次 all-reduce 的真实选路。部分卡对显示 SYS，不等于 TP8 的所有通信都经过 CPU。集体通信可能沿其他 XL 连接组成 Ring 或 Tree。

例如拓扑允许一条全 XL 的环：

```text
0 → 1 → 5 → 4 → 6 → 7 → 3 → 2 → 0
```

这里只证明有可行路径，没有证明运行时采用了它。真正的优化依据需要来自 BKCL 实际选路、各 rank 就绪时间和完成时间。

## 五、三台之间如何通信，网卡配对是否合理？

每台 eth0 是 100 Gb/s 管理/API 网口，eth1–4 各是 400 Gb/s，RoCE 端口报告 ACTIVE / LINK_UP。四组 P800 与网卡的就近关系为：

| P800 | NUMA | 400G NIC | RDMA 设备 |
|---|---:|---|---|
| XPU0/1 | 1 | eth1 | mlx5_1 |
| XPU2/3 | 3 | eth2 | mlx5_2 |
| XPU4/5 | 5 | eth3 | mlx5_3 |
| XPU6/7 | 7 | eth4 | mlx5_4 |

启动记录中的映射与此一致：

```text
BKCL_RDMA_NICS=eth1,eth1,eth2,eth2,eth3,eth3,eth4,eth4
```

因此没有发现明显的 GPU/NIC 配错问题。两张卡共用一个 400G 端口，仍需要查看同时传输时的表现；端口标称速率不能替代实际有效吞吐。

报告还区分了控制流与大张量数据：请求数据走 mlx5_1–4，Gloo 控制通信有使用 eth0 的启动记录。看到控制流停在 `recv` 时，应先问数据或调度信息有没有准备好，而不是立刻认为 100G 管理网太慢。

## 六、Kimi-K3 为什么采用 TP8×PP3？

目标模型有 93 层，hidden size 为 7168，包含 24 层 MLA 与 69 层 KDA。MoE 配置包含 896 个 routed experts，每 token 选择 16 个，另有两个 shared experts。W4A16 主要覆盖指定的 routed expert 权重，不等于整模型所有权重和状态都变成了 4 bit。

每台的八张卡执行 TP8，三台之间组成 PP3。一份模型实例使用 24 张卡：

| 节点 | 阶段 | 层号，从 1 开始 | MLA / KDA | 附加工作 |
|---|---:|---|---|---|
| 53 | PP0 | 1–31 | 7 / 24 | Embedding，发送 3 个残差块 |
| 55 | PP1 | 32–62 | 8 / 23 | 发送 6 个残差块 |
| 57 | PP2 | 63–93 | 9 / 22 | 8 个残差块，最终 norm 与输出头 |

代码中的层号从 0 开始，所以对应 0–30、31–61、62–92。TP rank 0–7 分摊每层张量；不能理解为同一台服务器中每张卡各自拿到不同的 31 层。当前记录没有启用独立 EP 分组。

TP 通信在层执行过程中发生得比较频繁，PP 则集中在阶段边界。因此，把 TP 留在机内、让跨机网络承担 PP 传递，是合理的起点。[vLLM 的常见多机部署方式](https://docs.vllm.ai/en/latest/serving/parallelism_scaling/)也采用“每机 GPU 数作为 TP、节点数作为 PP”的组合。

但“31 层均分”只是层数均衡。尾段 MLA 更多，还有输出头和不同的状态开销。早间服务快照中，每卡显存占用约为 83.6、89.1、92.4 GiB，尾段更紧。这些占用包含缓存、缓冲区与运行时分配，不能全部归为模型权重。

报告提出 32/32/29 作为候选，可以将 MLA 分成 8/8/8，并减少尾段层数。不过，前两段也会增加显存和工作量，只有真实阶段耗时和显存验收才能判断是否值得改。

## 七、活动率很不均，为什么不能直接搬层？

原诊断中，节点 53 的活动率接近 97%，节点 55、57 明显较低。直觉上容易认为前段过载、后段空闲。

设备时间线和 CPU 栈给出了更细的解释：前段的设备活动中有大量 stream wait；后段主线程可能停在 Gloo 接收，设备则没有任务。不同等待方式会产生不同的活动率表现。

P1 后的一段约 15.08 秒 decode trace，以采样的 XPU0 为例：

| 阶段 | 任务覆盖 | 显式 stream-wait 覆盖 | 不与显式等待重叠的任务时间 |
|---|---:|---:|---:|
| PP0 | 约 100% | 约 70% | 4.54 s |
| PP1 | 约 75.5% | 约 42.6% | 4.96 s |
| PP2 | 约 39.6% | 约 7.2% | 4.88 s |

后两段主线程约 62%–63% 的采样停在 `recv`。扣除显式等待后的任务时间明显比活动率更接近。

这仍然不是纯计算均衡的证明：任务中还可能包含通信与其他工作，trace 只采了部分卡，跨机时间对齐也有误差。但它足以阻止一个过强判断：不能按活动率比例把模型层从前段搬到后段。

## 八、当前通信瓶颈更像哪里？

### Prefill 占据了大部分首 token 延迟

原部署在 1024 输入 / 32 输出、零前缀命中、零新增抢占条件下：

| 并发 | 服务端 TTFT | Prefill 阶段 | 排队 |
|---:|---:|---:|---:|
| 16 | 8.724 s | 8.101 s | 约 0.000055 s |
| 32 | 15.971 s | 15.217 s | 约 0.131 s |

Prefill 阶段占 TTFT 约 93%–95%。这个指标包含计算、设备依赖和流水线等待，不能直接读成算子用了 15 秒。但它说明，仅优化 API 排队不足以解释和解决主要延迟。

### 裸传输是毫秒级，完整路径仍可能卡住

单卡、单 TP 分片的隔离 BKCL 微测中，PP0→PP1 的 84 MiB 接收中位时间约 3.25 ms，PP1→PP2 的 147 MiB 约 5.52 ms，并有数值校验。网络采样没有发现明显错误、重传或带宽耗尽证据。

这说明该尺寸的裸传输本身没有测出秒级耗时，却不能替代完整八 rank 测量。实际阶段传递还包括：

```text
CPU 准备与上游就绪
    → Gloo 元数据握手
    → TP 分片跨机发送
    → 接收端机内 all-gather
    → 下游 forward
    → 尾段采样及结果/token 返回
```

发送前等上游、接收后等 all-gather、下一步等 token 返回，都可能让三台不能充分重叠。当前更有依据的方向是缩短这些依赖等待，而不是先加网卡。

PP 的数据量也不是只传一份 hidden。当前路径发送 `hidden_states` 与多个 `residual` 块，再在接收端重建。三块与六块残差分别约对应四份与七份 hidden 大小的数据，后边界约是前边界的 1.75 倍。即使层数相同，通信和临时状态也会不同。

### 缓存补丁有小幅收益，但没有解决全部等待

P1 在实际安装包中缓存了设备上的 `block_sizes`，避免每步创建小设备张量时发生隐式同步。1024/1024 的四档单波短测输出吞吐增加约 3%–5%，但秒级 prefill/PP 等待仍然存在。

后续同为 1024/1024、32 并发的调度对照也很有启发：

| 配置 | 平均 TTFT | 输出吞吐 |
|---|---:|---:|
| 异步 P1 基线 | 15.85 s | 212.21 tokens/s |
| 同步 groups=0 控制组 | 11.23 s | 211.39 tokens/s |

首 token 更早，不等于总完成时间更短。以上是单波观测，尚不能宣称稳定的因果收益；记录中也没有 groups=3 微批次均衡的正式性能结果。

## 九、下一轮检测具体看哪些模块？

下一轮先找最长停顿所在的环节，再按证据决定优化。下面的入口来自已有源码快照，采集前要核对实际加载文件，尤其是独立的 DSpark 运行版本。

| 顺序 | 模块 | 重点入口或对象 | 要回答的问题 |
|---:|---|---|---|
| 1 | PP 控制流与图重放 | `send_object/recv_object`、`send_tensor_dict/recv_tensor_dict`、SDK `replay`、结果/token 返回 | 后段在等上游、元数据、设备依赖还是传输？ |
| 2 | 输入准备与缓存状态 | `_prepare_inputs`、`_build_attention_metadata`、`_get_slot_mappings`、KDA metadata | CPU 准备是否隐式等待之前的设备工作？ |
| 3 | TP / PP 数据通信 | 八 rank 的 all-reduce、all-gather、send/recv | 谁最晚就绪、谁最晚完成，是否有通信拖尾？ |
| 4 | 调度与执行器 | `schedule`、`step_with_batch_queue`、RPC/future | 是否形成了能交错运行的独立批次？ |
| 5 | CPU/NUMA 与主机缓冲 | 绑定列表、线程位置、`numa_maps` | 高频交换数据的线程和缓冲是否靠近 GPU？ |
| 6 | 模型实际计算 | KDA、MLA、MoE、残差处理、最终输出头 | 去掉等待后，哪个阶段或算子最慢？ |

输入准备尤其要检查每步的新建设备小张量、`.cpu()`、`.item()`、同步 copy 和重复分配。P1 已缓存的对象应确认持续复用，而不是反复把它当成未完成优化。KDA prefill 获取 CPU `query_start_loc` 是另一个重点候选，但必须确认真实执行分支。

通信测量应覆盖 decode 小张量与 prefill 大张量，并记录接收端 TP 重建。以前的单卡裸传输不能排除两 rank 共用 NIC、八卡集体通信或某个慢 rank 的影响。

调度应记录每步 prefill/decode token 数、请求数和在途批次。`max_concurrent_batches=3` 是容量设置，不是“已经有三个阶段持续计算”的证明。

## 十、怎样组织一次能解释问题的检测？

核心产物应该是一条能按 `batch_id` 关联的三机时间线，而不是再截三张活动率图。

每个事件至少带上 run、batch、PP stage、TP rank、主机、prefill/decode 类型、token 数、张量形状与字节数、stream 和时间戳。关联以下事件：

1. 调度产生批次，执行器发出任务。
2. CPU 输入和 metadata 准备完成。
3. 上游中间状态就绪，PP 元数据交换完成。
4. PP 数据提交以及设备侧完成。
5. 接收端 TP all-gather 完成。
6. 当前阶段 forward 的设备开始与完成。
7. 中间状态发送，或尾段采样完成。
8. 结果/token 返回，下一步具备调度条件。

CPU 调用返回不一定代表设备传输完成。跨机时间要校准，不能在时钟误差大于目标事件间隔时硬做毫秒级先后判断。重叠事件不能直接相加成 TTFT，也不能在每个测量边界强制全设备同步，破坏原本想观察的重叠。

功能与性能验收要分开。Prefill 定位可使用 1024/32；生成吞吐对照使用已约定的 1024/1024、并发 1/8/16/32。正式吞吐应在 profiler 退出后测量，同一组提示词、缓存策略、到达方式与运行参数下重复比较。

输出吞吐的口径是实际生成 token 总数除以第一请求发起到最后请求完成的整批时间。同时保留 TTFT 均值/P95、最后首 token、TPOT/ITL、错误、抢占、缓存命中和显存变化。一次波次中的 32 个请求不能当作 32 次独立重复实验。

## 十一、优化顺序与仍待验证的判断

接下来的优化顺序是：先消减输入准备和控制流同步，再验证 PP/TP/计算重叠与批次形状，之后检查 NUMA 与 BKCL 选路，最后按真实工作时间评估重分层。

`max_num_batched_tokens=16384` 可与 8192、6144 作单变量对照，但小批次也会增加调度和通信次数。官方调优文档将该参数视作延迟与吞吐之间的权衡，不能将“小一点”直接等同于“更快”。[vLLM 调优说明](https://docs.vllm.ai/en/latest/configuration/optimization/)。

NUMA 的目标 GPU worker 归属是 `1,1,3,3,5,5,7,7`。先看实际绑定与内存分布，再判断是否需要改变；一般 CPU 后台工作仍可利用其他节点。[NUMA 绑定说明](https://docs.vllm.ai/en/latest/configuration/optimization/#numa-binding-for-multi-socket-gpu-nodes)。

32/32/29 和 TP4×PP6 都属于候选，尚未验证收益。前者试图改善层类型与尾段工作量，后者试图利用四卡 XL 组，但都必须同时验收计算、通信、显存和功能正确性。异步优化也不能简单删除等待，需要保持张量生命周期、stream 依赖和结果顺序。

DSpark 要另设同版本 baseline/spec 对照。接受率统计需要排除 bonus token，并同时记录草稿、目标验证、通信和状态处理时间。高接受率不能自动推出高吞吐；只有新增成本被多 token 接受抵消，端到端指标才会改善。本文没有把尚未获得的新版本端到端数据写成收益结论。

## 补记：Eagle3 全量验证通过正确性门，仍未通过性能门

10 月 16 日完成的 r16 验证，把上文的“继续寻找投机路径”推进到了一个可以明确决策的阶段：完整目标权重成功加载，功能与 API 检查通过，但两轮正式输出吞吐都低于预设历史门槛，因此恢复了未开启 Eagle3 的 P1。这里的失败指性能保留条件没有满足，不是把之前的初始化失败或随机权重检查当成了完整模型结果。

### 从 PP 所有权修到真实状态语义

接入草稿模型时，不能假设所有 PP rank 都拥有同一个对象。目标模型在三个阶段都有工作，草稿侧的 Graph key 和 attention backend 却由实际拥有 drafter 的阶段初始化。修复必须同时保留每段目标模型的初始化，避免为了让非尾段“不报属性不存在”而跳过它自己的状态；真正应该拥有 drafter 的尾段缺失该对象时，仍应报错。这个区别让检查针对资源归属，而不是用宽泛的异常捕获把错误吞掉。

随后暴露的是多 token 路径的状态问题。一次验证多个候选 token 时，attention 的真实上下文长度、有效 token 行与 KDA 的递归状态和卷积历史必须互相对应。CPU 上的容量上界只能用于分配和调度，不能直接冒充每行在 GPU 上的精确有效长度。固定输入的 Q4 或 Graph replay 恰好通过，也不能代替纯 prefill、混合批次和长前缀的检查。

原生卷积对照进一步区分了两种问题：非连续的状态索引向量会错误寻址；带已有状态的长 prefill，则只在最前面三个输出位置出现差异，后面的输出和最终历史可以正常。候选先把索引规范为连续格式，再在受限定的候选路径中，用独立保存的输入与历史、沿 Q1 更新原语重算受影响的前缀输出。最终缓存仍由原路径完成更新。把历史打包成三个紧凑位置的替代尝试没有解决长前缀问题，因此未进入保留方案。

这不是“给整个模型改成高精度”的处理，也不是绕过差异比较。r16 在加载真实目标权重之前，先覆盖全部 24 rank 的完整 KDA 顺序 Q1 对照、输出与最终状态/历史检查、Graph 波次和原生卷积参照。报告分别保留 216 次完整 KDA 检查、72 次 KDA Graph 波次、960 个 greedy verifier 案例和 168 次直接卷积对照；它们验证不同边界，不能相加成同一种独立样本数。早期失败与未执行的诊断分支也保留在记录中，没有被后来的绿灯覆盖。

### 三层检查不能互相替代

原生门通过后，还有一次完整架构的 dummy 启动。它使用随机目标权重和真实草稿权重，只能证明初始化、协议与执行路径能够衔接，不能产生目标模型语义质量或性能结论。

随后才加载真实目标模型的全部 94 个分片，完成同一次启动中的 API 前检，再跑两轮冻结的 C32、每轮 160 请求、每请求 1024 输入与 1024 输出的正式负载，最后执行 API 后检和恢复检查。TP8×PP3、1M 上下文、请求默认值与既定协议保持约束；本轮没有为了让候选过门而重跑或重选历史基线。

| 记录 | 输出吞吐，tokens/s | 完成与证据范围 |
| --- | ---: | --- |
| 历史冻结基线 | 223.9508 | 本轮未重跑，作为预设保留门槛 |
| Eagle3 B1 | 115.0334 | 160/160，请求输出共 163,840 tokens |
| Eagle3 B2 | 115.7638 | 160/160，请求输出共 163,840 tokens |

吞吐仍按整批输出 token 数除以第一请求开始至最后请求完成的时间计算。两轮分别约为 1424.28 和 1415.30 秒；各自是一次批次测量，不是 160 次独立重复实验。正式负载没有前缀命中或抢占，API 前后合计 40/40 通过，冻结正确性检查合计 88/88 通过。这些有限检查支持本次验收，不证明所有输入与原模型逐位等价。

草稿 token 接受率约为 46.71% 和 47.23%，也没有换来更高吞吐。接受一个以上草稿 token，只说明目标验证能一次推进多个位置；草稿计算、多 token 验证、状态整理与流水线控制的新增成本仍然存在。本次报告能确定的是候选没有达到保留门槛，尚不能仅凭这张表把退化全部归因到某一项通信或算子开销。

### 为什么最后恢复原方案

相对历史基线，两轮观测值约低 48.63% 和 48.31%。由于历史基线没有在本轮重新执行，这不是随机交错 A/B，也不是对未来所有负载的因果或显著性结论；它足以支持事先约定的保留决策：两轮有效结果都没有超过门槛，候选不留在服务中。

最终记录为 `CLOSED_RESTORED`：恢复原 P1 后，健康检查、服务身份、实际源文件与依赖、1M 上下文均复核，三节点证据包已取回并校验。后续其他调优会话仍可能继续工作，因此这里描述的是这次已闭合实验的终态，而不是宣称现场从此不再变化。本次博客维护只读核对结果、修复差异与会话，没有连接服务器或重跑这些实验。

这段过程补齐了工程实践中的另一半：功能正确允许候选进入性能评估，性能门决定是否保留；恢复完成则需要自己的健康与身份验证。任何一个阶段都不能由前一阶段的“通过”代替。

## 十二、这次排查留下的几条判断习惯

对我而言，最有用的变化是把几个经常混在一起的概念拆开：

- socket 是物理 CPU；NUMA 是 CPU/内存访问域，两者数量不必相同。
- 主机 RAM 与 P800 显存分别计量，`MemTotal` 也不等于空闲容量。
- XL/PIX/SYS 描述拓扑条件，真实集体通信选路需要运行证据。
- GPU 活动率包含不同形式的等待，不能直接用于分层。
- 接收调用的等待时间与裸数据传输时间要分别测。
- 更低 TTFT 与更高输出吞吐是不同目标，必须分别验收。
- 能够指出“哪个批次、哪个 rank、在哪条依赖上卡住”，才有足够依据选择下一项优化。

本文的工程依据包括原瓶颈报告、模型配置与分层记录、实际安装包 P1 验证、decode 时间线、调度单波对照，以及三机硬件核查。单波收益、部分设备采样和未确认的交换机布线，都保留了它们的证据边界。
