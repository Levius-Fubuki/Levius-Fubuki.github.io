# 从 NUMA 到流水线：P800 三机部署 Kimi-K3 的拓扑与瓶颈笔记

这次排查从两个看似简单的问题开始：一台 P800 服务器里的卡是不是都通过 PCIe 通信？如果三台机器的加速器活动率差别很大，是不是模型层分配错了？

把设备拓扑、CPU/NUMA 归属和推理时间线放到一起后，我发现，这两个问题都不能只靠一张利用率截图回答。机内有专用的 XPULink，也有 PCIe 和跨 NUMA 路径；模型层数可以平均，等待方式却可能完全不同。

这篇笔记记录三台八卡 P800 运行 Kimi-K3 的结构，以及从已有实验中能得出什么、还不能得出什么。硬件核查时间是 2026 年 10 月 14 日；前半篇保留 10 月 13 日的诊断、短测与当时的优化计划。后续补记分别记录 10 月 16 日 Eagle3 的负结果、10 月 18 日执行栈优化后的正式复测，以及截至 10 月 22 日仍未闭合的一致性问题；这些属于不同版本，不能互相覆盖。为了保留工程关系而不暴露访问地址，文中使用节点 53、55、57 作为服务器编号。

## 一、先认识 P800：软件接口与实际硬件要分开看

P800 是昆仑芯的 AI 加速器，采用 XPU-P 架构。官方介绍中的 P800 OAM 模组依据 OCP-OAM 标准设计，支持通过 IB 或 RoCE 构建集群。这里讨论的是现场三台服务器的实际连接关系，而不是把厂商宣传中的某种超节点配置直接套进来。[架构介绍](https://www.kunlunxin.com/news/4720.html)、[OAM 与互连介绍](https://www.kunlunxin.com/news/4791.html)。

现场每台有八张 P800，每卡显存 96 GiB。使用中的软件栈包含 vLLM、昆仑插件、XPU SDK 和 BKCL 通信库。环境里能看到 `nvidia-smi`、`torch.cuda`、CUDA 风格的 stream 和 graph 接口，但这些接口名字不能作为 NVIDIA GPU 或 NVLink 硬件的证明。分析性能时，要沿着实际加载的昆仑实现追踪。

这也解释了为什么排查时必须核对运行路径：改了工作区代码，不代表安装包中的插件已经更新。之前一次“四补丁评估”就因为改动没有进入实际执行路径而撤回。随后 P1 补丁才在真正加载的安装包中完成验证。

## 三、2 sockets、8 NUMA，为什么图中曾经只有四个分支？

一台服务器有两颗物理 CPU，也就是 **2 sockets**。三台都是双路 Hygon C86 P455，每颗 64 核、128 线程，整机合计 128 核、256 线程。

NUMA 不是 CPU 插槽的另一种叫法。它是操作系统描述 CPU 核和内存就近关系的局部域。同一颗物理 CPU 可以划分成多个 NUMA 节点。

实际 `lscpu` 映射确认：

- socket 0 包含 NUMA 0、1、2、3。
- socket 1 包含 NUMA 4、5、6、7。
- 每个 NUMA 都有 16 核、32 线程及对应的主机内存。

之前只画了 P800 和 400G 网卡所在的 NUMA 1、3、5、7，所以看起来像整机只有四个 NUMA。完整图补齐了其他四个节点，并加入 NUMA 0 上的管理网卡 eth0。

| NUMA | Socket | CPU 逻辑编号 | 主机 RAM，约 GiB | 本图涉及的设备 |
|---:|---:|---|---:|---|
| 0 | 0 | 0–15, 128–143 | 187.9 | eth0，100G |
| 1 | 0 | 16–31, 144–159 | 188.5 | XPU0/1、eth1 |
| 2 | 0 | 32–47, 160–175 | 188.5 | CPU / 主机内存 |
| 3 | 0 | 48–63, 176–191 | 188.5 | XPU2/3、eth2 |
| 4 | 1 | 64–79, 192–207 | 188.5 | CPU / 主机内存 |
| 5 | 1 | 80–95, 208–223 | 188.5 | XPU4/5、eth3 |
| 6 | 1 | 96–111, 224–239 | 188.5 | CPU / 主机内存 |
| 7 | 1 | 112–127, 240–255 | 184.5 | XPU6/7、eth4 |

表中的逻辑 CPU 编号包含 SMT 线程，不能把 32 个逻辑编号读成 32 个物理核。

### 相对距离描述什么？

以 NUMA 4 为例，到 NUMA 0–7 的距离为：

```text
目标节点：  0   1   2   3   4   5   6   7
相对距离： 25  27  27  27  10  15  15  15
```

从 NUMA 4 的 CPU 核出发，访问本节点内存的距离是 10；访问同一颗 CPU 内其他节点的内存是 15；跨到另一颗 CPU 是 25 或 27。

这些数值是固件报告的相对访问距离。它们不是纳秒、带宽，也不能说明实际延迟就是本地访问的 2.7 倍。它们描述的是 CPU 与主机内存的关系，不是 P800 的 XPULink 速度。

### MemTotal 与显存为什么必须分开？

NUMA 的 `MemTotal` 是操作系统报告的主机 RAM 总容量，不是当前剩余可用内存，也不是加速器显存。OS 管理的容量可能略少于内存条的标称容量。

例如 NUMA 5 有约 188.5 GiB 主机 RAM，附近的 XPU4、XPU5 又各有 96 GiB 显存。这些是不同的内存资源。模型加载通常涉及主机到设备的数据传输，设备计算主要使用卡上的显存，不能把这些数字直接当作一块统一的高速内存池。

### NUMA 2、4、6 是否没用到？

没有挂接本图中的 P800 或 400G 网卡，不等于没有工作。它们仍可运行分词、请求调度、模型加载、后台进程，也可承载主机内存分配。

如果没有限制线程与内存归属，Linux 可能使用这些节点。它们在某次推理中到底用了多少，要看 worker 绑定、线程位置和 `numa_maps`。对性能更有意义的问题是：频繁与 P800 交换数据的 CPU 线程和缓冲区，是否靠近对应的加速器？

## 四、卡间是不是都走 PCIe？

三台卡间矩阵一致，机内存在两类需要区分的连接：

1. **XPULink 路径。** XPU0–3 组内全连接，XPU4–7 组内全连接，跨组还有 0↔4、1↔5、2↔6、3↔7。
2. **PCIe / NUMA 路径。** 工具将其余部分卡对报告为 SYS；GPU 与近端网卡之间则报告 PIX。

八卡共有 16 个 XL 卡对，每卡四个 XL 邻居；其他 12 个卡对报告 SYS。

| 标签 | 工具报告的含义 |
|---|---|
| XL | 路径经过 XPULink |
| PIX | 路径至多经过一个 PCIe bridge |
| SYS | 路径经过 PCIe 与跨 NUMA 的 CPU 互连 |

这个矩阵告诉我们设备的连接条件，却不能直接告诉我们 BKCL 一次 all-reduce 的真实选路。部分卡对显示 SYS，不等于 TP8 的所有通信都经过 CPU。集体通信可能沿其他 XL 连接组成 Ring 或 Tree。

例如拓扑允许一条全 XL 的环：

```text
0 → 1 → 5 → 4 → 6 → 7 → 3 → 2 → 0
```

这里只证明有可行路径，没有证明运行时采用了它。真正的优化依据需要来自 BKCL 实际选路、各 rank 就绪时间和完成时间。

## 五、三台之间如何通信，网卡配对是否合理？

每台 eth0 是 100 Gb/s 管理/API 网口，eth1–4 各是 400 Gb/s，RoCE 端口报告 ACTIVE / LINK_UP。四组 P800 与网卡的就近关系为：

| P800 | NUMA | 400G NIC | RDMA 设备 |
|---|---:|---|---|
| XPU0/1 | 1 | eth1 | mlx5_1 |
| XPU2/3 | 3 | eth2 | mlx5_2 |
| XPU4/5 | 5 | eth3 | mlx5_3 |
| XPU6/7 | 7 | eth4 | mlx5_4 |

启动记录中的映射与此一致：

```text
BKCL_RDMA_NICS=eth1,eth1,eth2,eth2,eth3,eth3,eth4,eth4
```

因此没有发现明显的 GPU/NIC 配错问题。两张卡共用一个 400G 端口，仍需要查看同时传输时的表现；端口标称速率不能替代实际有效吞吐。

报告还区分了控制流与大张量数据：请求数据走 mlx5_1–4，Gloo 控制通信有使用 eth0 的启动记录。看到控制流停在 `recv` 时，应先问数据或调度信息有没有准备好，而不是立刻认为 100G 管理网太慢。

## 六、Kimi-K3 为什么采用 TP8×PP3？

目标模型有 93 层，hidden size 为 7168，包含 24 层 MLA 与 69 层 KDA。MoE 配置包含 896 个 routed experts，每 token 选择 16 个，另有两个 shared experts。W4A16 主要覆盖指定的 routed expert 权重，不等于整模型所有权重和状态都变成了 4 bit。

每台的八张卡执行 TP8，三台之间组成 PP3。一份模型实例使用 24 张卡：

| 节点 | 阶段 | 层号，从 1 开始 | MLA / KDA | 附加工作 |
|---|---:|---|---|---|
| 53 | PP0 | 1–31 | 7 / 24 | Embedding，发送 3 个残差块 |
| 55 | PP1 | 32–62 | 8 / 23 | 发送 6 个残差块 |
| 57 | PP2 | 63–93 | 9 / 22 | 8 个残差块，最终 norm 与输出头 |

代码中的层号从 0 开始，所以对应 0–30、31–61、62–92。TP rank 0–7 分摊每层张量；不能理解为同一台服务器中每张卡各自拿到不同的 31 层。当前记录没有启用独立 EP 分组。

TP 通信在层执行过程中发生得比较频繁，PP 则集中在阶段边界。因此，把 TP 留在机内、让跨机网络承担 PP 传递，是合理的起点。[vLLM 的常见多机部署方式](https://docs.vllm.ai/en/latest/serving/parallelism_scaling/)也采用“每机 GPU 数作为 TP、节点数作为 PP”的组合。

但“31 层均分”只是层数均衡。尾段 MLA 更多，还有输出头和不同的状态开销。早间服务快照中，每卡显存占用约为 83.6、89.1、92.4 GiB，尾段更紧。这些占用包含缓存、缓冲区与运行时分配，不能全部归为模型权重。

报告提出 32/32/29 作为候选，可以将 MLA 分成 8/8/8，并减少尾段层数。不过，前两段也会增加显存和工作量，只有真实阶段耗时和显存验收才能判断是否值得改。

## 七、活动率很不均，为什么不能直接搬层？

原诊断中，节点 53 的活动率接近 97%，节点 55、57 明显较低。直觉上容易认为前段过载、后段空闲。

设备时间线和 CPU 栈给出了更细的解释：前段的设备活动中有大量 stream wait；后段主线程可能停在 Gloo 接收，设备则没有任务。不同等待方式会产生不同的活动率表现。

P1 后的一段约 15.08 秒 decode trace，以采样的 XPU0 为例：

| 阶段 | 任务覆盖 | 显式 stream-wait 覆盖 | 不与显式等待重叠的任务时间 |
|---|---:|---:|---:|
| PP0 | 约 100% | 约 70% | 4.54 s |
| PP1 | 约 75.5% | 约 42.6% | 4.96 s |
| PP2 | 约 39.6% | 约 7.2% | 4.88 s |

后两段主线程约 62%–63% 的采样停在 `recv`。扣除显式等待后的任务时间明显比活动率更接近。

这仍然不是纯计算均衡的证明：任务中还可能包含通信与其他工作，trace 只采了部分卡，跨机时间对齐也有误差。但它足以阻止一个过强判断：不能按活动率比例把模型层从前段搬到后段。

## 八、当前通信瓶颈更像哪里？

### Prefill 占据了大部分首 token 延迟

原部署在 1024 输入 / 32 输出、零前缀命中、零新增抢占条件下：

| 并发 | 服务端 TTFT | Prefill 阶段 | 排队 |
|---:|---:|---:|---:|
| 16 | 8.724 s | 8.101 s | 约 0.000055 s |
| 32 | 15.971 s | 15.217 s | 约 0.131 s |

Prefill 阶段占 TTFT 约 93%–95%。这个指标包含计算、设备依赖和流水线等待，不能直接读成算子用了 15 秒。但它说明，仅优化 API 排队不足以解释和解决主要延迟。

### 裸传输是毫秒级，完整路径仍可能卡住

单卡、单 TP 分片的隔离 BKCL 微测中，PP0→PP1 的 84 MiB 接收中位时间约 3.25 ms，PP1→PP2 的 147 MiB 约 5.52 ms，并有数值校验。网络采样没有发现明显错误、重传或带宽耗尽证据。

这说明该尺寸的裸传输本身没有测出秒级耗时，却不能替代完整八 rank 测量。实际阶段传递还包括：

```text
CPU 准备与上游就绪
    → Gloo 元数据握手
    → TP 分片跨机发送
    → 接收端机内 all-gather
    → 下游 forward
    → 尾段采样及结果/token 返回
```

发送前等上游、接收后等 all-gather、下一步等 token 返回，都可能让三台不能充分重叠。当前更有依据的方向是缩短这些依赖等待，而不是先加网卡。

PP 的数据量也不是只传一份 hidden。当前路径发送 `hidden_states` 与多个 `residual` 块，再在接收端重建。三块与六块残差分别约对应四份与七份 hidden 大小的数据，后边界约是前边界的 1.75 倍。即使层数相同，通信和临时状态也会不同。

### 缓存补丁有小幅收益，但没有解决全部等待

P1 在实际安装包中缓存了设备上的 `block_sizes`，避免每步创建小设备张量时发生隐式同步。1024/1024 的四档单波短测输出吞吐增加约 3%–5%，但秒级 prefill/PP 等待仍然存在。

后续同为 1024/1024、32 并发的调度对照也很有启发：

| 配置 | 平均 TTFT | 输出吞吐 |
|---|---:|---:|
| 异步 P1 基线 | 15.85 s | 212.21 tokens/s |
| 同步 groups=0 控制组 | 11.23 s | 211.39 tokens/s |

首 token 更早，不等于总完成时间更短。以上是单波观测，尚不能宣称稳定的因果收益；记录中也没有 groups=3 微批次均衡的正式性能结果。

## 九、下一轮检测具体看哪些模块？

下一轮先找最长停顿所在的环节，再按证据决定优化。下面的入口来自已有源码快照，采集前要核对实际加载文件，尤其是独立的 DSpark 运行版本。

| 顺序 | 模块 | 重点入口或对象 | 要回答的问题 |
|---:|---|---|---|
| 1 | PP 控制流与图重放 | `send_object/recv_object`、`send_tensor_dict/recv_tensor_dict`、SDK `replay`、结果/token 返回 | 后段在等上游、元数据、设备依赖还是传输？ |
| 2 | 输入准备与缓存状态 | `_prepare_inputs`、`_build_attention_metadata`、`_get_slot_mappings`、KDA metadata | CPU 准备是否隐式等待之前的设备工作？ |
| 3 | TP / PP 数据通信 | 八 rank 的 all-reduce、all-gather、send/recv | 谁最晚就绪、谁最晚完成，是否有通信拖尾？ |
| 4 | 调度与执行器 | `schedule`、`step_with_batch_queue`、RPC/future | 是否形成了能交错运行的独立批次？ |
| 5 | CPU/NUMA 与主机缓冲 | 绑定列表、线程位置、`numa_maps` | 高频交换数据的线程和缓冲是否靠近 GPU？ |
| 6 | 模型实际计算 | KDA、MLA、MoE、残差处理、最终输出头 | 去掉等待后，哪个阶段或算子最慢？ |

输入准备尤其要检查每步的新建设备小张量、`.cpu()`、`.item()`、同步 copy 和重复分配。P1 已缓存的对象应确认持续复用，而不是反复把它当成未完成优化。KDA prefill 获取 CPU `query_start_loc` 是另一个重点候选，但必须确认真实执行分支。

通信测量应覆盖 decode 小张量与 prefill 大张量，并记录接收端 TP 重建。以前的单卡裸传输不能排除两 rank 共用 NIC、八卡集体通信或某个慢 rank 的影响。

调度应记录每步 prefill/decode token 数、请求数和在途批次。`max_concurrent_batches=3` 是容量设置，不是“已经有三个阶段持续计算”的证明。

## 十、怎样组织一次能解释问题的检测？

核心产物应该是一条能按 `batch_id` 关联的三机时间线，而不是再截三张活动率图。

每个事件至少带上 run、batch、PP stage、TP rank、主机、prefill/decode 类型、token 数、张量形状与字节数、stream 和时间戳。关联以下事件：

1. 调度产生批次，执行器发出任务。
2. CPU 输入和 metadata 准备完成。
3. 上游中间状态就绪，PP 元数据交换完成。
4. PP 数据提交以及设备侧完成。
5. 接收端 TP all-gather 完成。
6. 当前阶段 forward 的设备开始与完成。
7. 中间状态发送，或尾段采样完成。
8. 结果/token 返回，下一步具备调度条件。

CPU 调用返回不一定代表设备传输完成。跨机时间要校准，不能在时钟误差大于目标事件间隔时硬做毫秒级先后判断。重叠事件不能直接相加成 TTFT，也不能在每个测量边界强制全设备同步，破坏原本想观察的重叠。

功能与性能验收要分开。Prefill 定位可使用 1024/32；生成吞吐对照使用已约定的 1024/1024、并发 1/8/16/32。正式吞吐应在 profiler 退出后测量，同一组提示词、缓存策略、到达方式与运行参数下重复比较。

输出吞吐的口径是实际生成 token 总数除以第一请求发起到最后请求完成的整批时间。同时保留 TTFT 均值/P95、最后首 token、TPOT/ITL、错误、抢占、缓存命中和显存变化。一次波次中的 32 个请求不能当作 32 次独立重复实验。

## 十一、优化顺序与仍待验证的判断

接下来的优化顺序是：先消减输入准备和控制流同步，再验证 PP/TP/计算重叠与批次形状，之后检查 NUMA 与 BKCL 选路，最后按真实工作时间评估重分层。

`max_num_batched_tokens=16384` 可与 8192、6144 作单变量对照，但小批次也会增加调度和通信次数。官方调优文档将该参数视作延迟与吞吐之间的权衡，不能将“小一点”直接等同于“更快”。[vLLM 调优说明](https://docs.vllm.ai/en/latest/configuration/optimization/)。

NUMA 的目标 GPU worker 归属是 `1,1,3,3,5,5,7,7`。先看实际绑定与内存分布，再判断是否需要改变；一般 CPU 后台工作仍可利用其他节点。[NUMA 绑定说明](https://docs.vllm.ai/en/latest/configuration/optimization/#numa-binding-for-multi-socket-gpu-nodes)。

32/32/29 和 TP4×PP6 都属于候选，尚未验证收益。前者试图改善层类型与尾段工作量，后者试图利用四卡 XL 组，但都必须同时验收计算、通信、显存和功能正确性。异步优化也不能简单删除等待，需要保持张量生命周期、stream 依赖和结果顺序。

DSpark 要另设同版本 baseline/spec 对照。接受率统计需要排除 bonus token，并同时记录草稿、目标验证、通信和状态处理时间。高接受率不能自动推出高吞吐；只有新增成本被多 token 接受抵消，端到端指标才会改善。本文没有把尚未获得的新版本端到端数据写成收益结论。

## 补记：Eagle3 全量验证通过正确性门，仍未通过性能门

10 月 16 日完成的 r16 验证，把上文的“继续寻找投机路径”推进到了一个可以明确决策的阶段：完整目标权重成功加载，功能与 API 检查通过，但两轮正式输出吞吐都低于预设历史门槛，因此恢复了未开启 Eagle3 的 P1。这里的失败指性能保留条件没有满足，不是把之前的初始化失败或随机权重检查当成了完整模型结果。

### 从 PP 所有权修到真实状态语义

接入草稿模型时，不能假设所有 PP rank 都拥有同一个对象。目标模型在三个阶段都有工作，草稿侧的 Graph key 和 attention backend 却由实际拥有 drafter 的阶段初始化。修复必须同时保留每段目标模型的初始化，避免为了让非尾段“不报属性不存在”而跳过它自己的状态；真正应该拥有 drafter 的尾段缺失该对象时，仍应报错。这个区别让检查针对资源归属，而不是用宽泛的异常捕获把错误吞掉。

随后暴露的是多 token 路径的状态问题。一次验证多个候选 token 时，attention 的真实上下文长度、有效 token 行与 KDA 的递归状态和卷积历史必须互相对应。CPU 上的容量上界只能用于分配和调度，不能直接冒充每行在 GPU 上的精确有效长度。固定输入的 Q4 或 Graph replay 恰好通过，也不能代替纯 prefill、混合批次和长前缀的检查。

原生卷积对照进一步区分了两种问题：非连续的状态索引向量会被要求连续布局的 native 接口拒绝；带已有状态的长 prefill，则只在最前面三个输出位置出现差异，后面的输出和最终历史可以正常。候选先把索引规范为连续格式，再在受限定的候选路径中，用独立保存的输入与历史、沿 Q1 更新原语重算受影响的前缀输出。最终缓存仍由原路径完成更新。把历史打包成三个紧凑位置的替代尝试没有解决长前缀问题，因此未进入保留方案。

这不是“给整个模型改成高精度”的处理，也不是绕过差异比较。r16 在加载真实目标权重之前，先覆盖全部 24 rank 的完整 KDA 顺序 Q1 对照、输出与最终状态/历史检查、Graph 波次和原生卷积参照。报告分别保留 216 次完整 KDA 检查、72 次 KDA Graph 波次、960 个 greedy verifier 案例和 168 次直接卷积对照；它们验证不同边界，不能相加成同一种独立样本数。早期失败与未执行的诊断分支也保留在记录中，没有被后来的绿灯覆盖。

## 后续：从依赖修复到正式复测，成绩必须绑定具体版本

10 月 18 日的完整记录，使“先减少等待，再判断算子”的路线有了更具体的实现与结果。早期 r16 未通过性能门的事实仍然成立；随后恢复异步执行、修复依赖和验证其他候选，才得到新的阶段成绩。实验编号也有不同序列：10 月 16 日的完整权重 r16，与后来的 relay r16 逐层观测不是同一轮。

### 调度和保留页依赖怎样影响流水线

真实 Scheduler / EngineCore 回放中，V1 异步路径能够形成单批 32，某些同步配置则形成 16＋16。批次拆分会改变权重复用与通信次数，不能只看有效 token 总数。真实 MoE 组件在同为 32 个有效 token 时，单批约 1.033 ms，两批约 1.553 ms，三批约 2.011 ms；这些是组件观测，不是整模每步时间。

异步恢复还涉及 PP 的反馈和对象生命周期。后台 transport 需要正确的推理执行上下文，反馈 future 必须归属实际批次；设备调用与 Graph capture 的互斥也不能把 Gloo 或 Future 的等待包在锁里，否则本来可以交错的工作又会串行。前文缓存 slot mapping 小张量的 P1 保留在这条路径中，没有把已完成的缓存优化再算成新收益。

另一处直接修复发生在 NULL 保留页。独立请求共享保留页标记时，旧 fence 把它当作真实共享块，额外建立跨批次依赖。补丁过滤非正块 ID，同时继续追踪真实共享页。合成 TP8／PP3 流水线组件测得约 2.54 倍完成速度，后续整模两轮为 239.1221／243.6445 tokens/s。组件倍率只描述那个合成实验；整模还包含目标计算、草稿、输入准备和状态管理，不能照搬倍率。

### 共享 KDA Graph 跑通以后，为什么仍不能直接宣称单项加速

混合 prefill 会改变边界和页映射，Graph 的 key、输入指针、状态所有权和回退都需要覆盖。早期 r22 虽通过 API 与有限数值检查，正式 160 请求只成功 33 条：冷 capture 先在页映射构造处报错，随后出现 PP 行序保护报错并退出。该轮无有效吞吐，删掉后出现的保护也不能解决前面的错误。

后续候选让私有 Graph 创建与 PP 反馈设备调用共享 RLock，阻塞等待留在锁外。测试隔离也经历过修正：显存拒绝测试先碰到了已耗尽的 capture 数量上限，不能把这一退出写成整套通过；换用独立 manager 验证各自拒绝条件后，八 rank 才全部正常退出。这里修复的是测试条件，没有把同一份生产保护算作第二次优化。

r25 B 使用合格组件完成同一次启动下的两轮正式测试，吞吐为 **247.5310／247.5436 tokens/s**，各 160/160 请求、44/44 固定答案，合并口径为 247.5373。24 个 worker 都记录到共享 Graph 命中，共 73,968 次层调用。约 160.13 MiB/worker 的统计只覆盖私有子 Graph，不是进程显存。

但配对 A 恢复后未通过 NUM36，A1/A2 没有执行。A 对应原 EAGLE3 D3，也不是未开启投机的 P1。因此，这两轮能证明候选在已测窗口完成工作，不能独立量化“共享 Graph 带来多少收益”。后面的 r30 又关闭了该子 Graph，转而诊断有界投影；它首轮有五项不等价，未测正式吞吐，也不能继承 r25 的成绩。

### 组件反例与后续状态仍然影响下一轮选择

MLA 的原生 Q4 组件曾通过普通输入波次，却在端点毒化时与顺序 Q1 出现 59 个元素差异，最大绝对差约 3.81e-6。同一波 Graph 与 eager 相同，说明至少不能把这组反例归为 Graph replay 不稳定。固定容差通过与要求逐字节一致，是两种验收目标。

串行 native Q1 回退随后通过 10 配置、58 波输入变化与生命周期检查，但 C32／Q4 的 1K、8K 核心成本比紧凑旧 Q1 分别高约 8.88% 和 11.07%。私有入口还有 metadata 与数据准备成本，不能只挑宽表旧实现作对照，也不能继承 native Q4 的核心倍率。通信四臂的单机 TP8 链测试同样没有确认实用收益，不能写成三机通信已解决。

截至 10 月 22 日的较新封存记录中，r160 只通过 35/36 一致性检查；它没有新吞吐成绩。另一条 R6 非投机底座的 DSpark 适配线也未完成整模资格：固定答案能返回，不代表普通／teacher-forced／投机输出已经等价。CPU 状态契约、原生小张量与 Graph 组件通过，只能支持继续集成。缺少真实权重的后续阶段更不能补出性能结果。

这组结果的价值在于把具体修复和可用结论对应起来：NULL 依赖、批次形状与反馈交接有直接实现依据；Graph 候选有自己的命中和失败记录；最终性能绑定恢复后的 R6。新的实验只能带着自己的正确性、负载与版本证据向前推进。

## 从一次 D3 验证串起整条推理链

这段复盘跟着同一个请求从 prompt 走到下一轮 decode。案例中的 token 和矩阵尺寸用来解释执行关系，性能数字来自后面单列的实测。上面的拓扑图可以配合案例查看卡、网口与 PP 阶段的归属。

### 权重、激活与持久状态

线性层可以写成 `Y = XWᵀ`。`W` 是已加载的模型参数，`X` 是当前请求在这一层产生的输入特征，`Y` 是输出特征。这里的激活包含层间 hidden states 和投影结果，不局限于 SiLU 一类激活函数的输出。

| 对象 | 在这次部署中怎么表示 | 生命周期 |
| --- | --- | --- |
| 路由专家的 gate、up、down 权重 | 对称、静态、per-channel 的 packed INT4 | 加载后供不同请求复用 |
| 主路径 hidden states | FP16 | 由当前请求和执行步骤产生 |
| 量化 scale、router logits | 对应路径使用 FP32 | scale 随权重加载，logits 随本轮路由计算 |
| MLA latent cache | 按历史 token 管理的缓存 | 请求持续期间可被后续 query 访问 |
| KDA 卷积历史与递推状态 | 卷积历史与 FP32 递推矩阵分别管理 | 本轮读写，提交后供下一轮续接 |

W4A16 中的 A16 指激活表示。检查点配置标注 BF16，正式服务的主运行 dtype 为 FP16，算子内部累加与状态 dtype 还要按各自实现判断。按通道量化可以理解成每个输出通道有自己的 scale。比如一行权重覆盖约 ±0.1，另一行覆盖 ±10，分别设定 scale 能给小值保留更多可用编码。反量化后的近似权重可写成 `W_hat[o,i] = scale[o] × q[o,i]`。

检查点主要把路由专家的 `w1/w3/w2` 打包成 4-bit 权重。共享专家、router、attention、embedding、LM head、latent MoE 的升降维与部分归一化保留浮点表示。昆仑插件加载后重排 packed 权重、调整位编码，并转换 scale 以匹配 native kernel 的约定。把已打包的数据视为 INT8 存储容器时，一个字节仍可装两个 4-bit 编码。被量化矩阵的数据部分理论上缩到 FP16 的四分之一，整机显存还包含未量化权重、scale、KV、状态、通信与 Graph 缓冲。吞吐收益需要用相同配置实测。[权重量化与 A16 的通用说明](https://nvidia.github.io/TensorRT-LLM/1.0.0/reference/precision.html#int4-and-int8-weight-only-w4a16-and-w8a16)

### 目标模型怎样利用三台机器

文本主干是 hidden size 7168 的 93 层 decoder。前 92 层按三个 KDA 接一个 MLA 的模式排列，第 93 层再用 MLA，共 69 层 KDA、24 层 MLA。第一层用 Dense MLP，其余层用 latent MoE。路由分支每 token 从 896 个专家选 16 个，在 3584 维 latent 空间计算，再投影回 7168。共享分支使用原始 hidden 计算。AttnRes 按块聚合模型深度方向的残差信息。

三台各八卡，合计 24 张 96 GiB P800。每台的八卡分摊同一阶段的层内张量，三个阶段分别执行第 1–31、32–62、63–93 层。每台内部是两个四卡 XPULink 全连接组，再加对应卡的跨组连接。层内频繁的集合通信留在本节点，跨阶段传递 hidden、残差和逐步收集的 EAGLE3 辅助特征。拓扑图给出连接条件和网口亲和性，运行时的集合通信选路与链路完成时间需要另测。

KDA 的 96 个头在 TP8 下每卡 12 个头。单请求、单层、单分片的一个 FP32 递推矩阵为 `12 × 128 × 128 × 4 = 786432 bytes`，即 0.75 MiB。MLA 则保存按 token 组织的压缩表示，项目中每个历史位置的表示宽度为 512 + 64。目标 MLA 使用 NoPE，配置字段里的 `qk_rope_head_dim` 表示维度，目标实现的 rotary 开关决定是否旋转。两类 attention 的差别直接影响投机回退，MLA 通过有效长度限制可见历史，KDA 要选择对应前缀的矩阵和卷积历史。

1. **Prefill 与辅助特征。** 目标模型的三个 PP 阶段依次消费 prompt，捕获配置指定的辅助点 2、46、90。前两级将已得到的特征与正常中间结果一起向下游发送。末级汇集三份特征，拼接后由草稿模型的 FC 融合，并根据目标采样得到的首个输出 `t0` 生成三个候选 `a,b,c`。
2. **本轮验证。** 下一次目标前向的输入是 `[t0,a,b,c]`。D3 指三个草稿候选，Q4 指目标需要处理的四个 query 位置。目标前向仍穿过全部三个阶段。每个阶段持有自己负责层的权重、MLA cache 和 KDA 状态。
3. **拒绝与提交。** 假设验证接受 `a,b`、拒绝 `c`，并由目标模型输出替代 token `z`。本轮对外输出 `[a,b,z]`。保留的 KDA 状态对应已消费 `[t0,a,b]`，`z` 在下一轮进入目标前向。MLA 的逻辑有效长度也要排除拒绝后缀。
4. **末级生成下一轮草稿。** 完整 draft 放在末级节点的 TP8 组，draft 构造按 PP1 处理。末级根据本轮有效结果和对应目标特征生成新候选 `[e1,e2,e3]`。反馈包含本轮输出、下一轮候选、最后有效输出、有效数量与源位置。D3 的反馈行包含 10 个 INT64 元素，结构为 4 个输出槽、3 个候选槽、最后有效输出、数量和源位置。示例中的有效输出数为 3，已接受草稿数为 2。
5. **反馈与状态交接。** 各 PP 组通过后台 CPU/Gloo 路径接收反馈。在本地按请求身份、generation 和生产轮次找回对应行，再按接受边界发布各层状态。前向中间张量走阶段间发送，控制反馈通过 D2H、CPU 广播和 H2D 返回。每个阶段先提交向下游的前向发送，末级才有数据产生反馈。Future 返回设备 event 后，对应消费者还要等待该 event。
6. **调度和本轮输入准备。** CPU Scheduler 选择本轮请求、token 预算和缓存资源。它可以先预留三个投机位置，GPU worker 在消费该请求前用真实反馈替换占位语义，构造 `[z,e1,e2,e3]`。反馈提供真实 token、计数和源位置，页表则来自本地缓存分配。随后 runner 组装本轮 query 边界、位置、长度和槽位。
7. **Graph 重放。** 候选接受数可以变化。请求继续完整 D3 时，下一轮验证仍有四个位置，改变的是 token、位置、有效长度和状态索引。Graph 可以读写预先分配的固定地址，每轮更新 buffer 内容。实际批次大小变化时，按 token 几何选择可用形状桶，适用时补齐容量并保护无效行。Draft 的 padded 准备保留拒绝后缀占用的行，用有效计数和采样索引选择正确位置，再修正历史长度。Graph 覆盖范围取决于模式、shape 与后端资格。[CUDA Graph 的重放约束](https://docs.pytorch.org/docs/main/notes/cuda.html#cuda-graphs)

同一个 D3 配置下，如果本轮只接受 0 个候选，有效输出通常是一个目标替代 token。全接受时可以提交三个候选加一个目标 bonus。反馈中的最后有效输出为下轮的衔接 token，已提交的其余 token 不必作为整段输入再处理。

### 把容易混在一起的三类信息分开

**反馈是上一轮的记录。** 它说明验证产生了什么、下一轮草稿是什么、该从哪里继续。**Metadata 是本轮算子的输入说明。** 例如请求 A、B、C 分别有 4、3、1 行 query 时，打包边界为 `query_start_loc = [0,4,7,8]`。`seq_lens` 确定上下文可见范围，`block_table` 将逻辑页映射到物理页，`slot_mapping` 描述当前写槽。**Builder 是组织这些数据的代码。** MLA builder 把通用 batch 信息转换成当前 MLA 后端能读的 metadata，KDA 的 builder 还要准备状态索引等字段。

异步投机时，CPU 可能先假设上一轮草稿全接受。比如 CPU 估计已计算 104 个位置，设备根据接受结果确认实际为 103；再安排 4 个 query 后，CPU 上界为 108，设备长度为 107。CPU 上界供 host 准备，实际因果读取仍需要校正后的长度。早期 unpadded 转换裁掉 padding 时漏传了 `seq_lens_cpu_upper_bound`，修复是随其余请求字段一起切片。

第三类信息是**线程执行上下文**。这里的 `inference_mode` 是 PyTorch 对当前线程生效的运行设置。RPC 是进程间发起 worker 调用的机制，transport 负责反馈传输，`ThreadPoolExecutor` 把部分任务交给后台线程。主线程的模式不会随函数和参数一起传给后台线程。项目中启动与 Graph 预检通过，第一条真实 API 进入后台拷贝和回调才报错。后来在统一提交入口显式进入推理模式。设备、stream、event 和 buffer 生命周期各有自己的约束。[PyTorch inference_mode](https://docs.pytorch.org/docs/stable/generated/torch.autograd.grad_mode.inference_mode.html)

<h3 id="q4-metadata-builder">Q4 到底改了哪个字段？</h3>

假设请求 A 本轮处理四个 query，B 处理一个。打包偏移是 `query_start_loc=[0,4,5]`。A 取第 0 到 3 行，B 取第 4 行。若 A 此前已计算 100 个位置，它的四行分别能看到 101、102、103、104 个位置。历史的 100 个位置通过长度和 KV 页表描述，本轮的 4 个位置才进入打包偏移。Prefill 时，尚未计算但本轮已调度的 prompt token 也计入偏移。CPU 长度上界用于 host 规划，设备上的精确长度用于决定每行实际访问的历史范围。

Runner 按验证几何生成 `max_query_len=4`。原先子类的 `build_for_cudagraph_capture()` 调父类，父类先检查 `max_query_len <= reorder_batch_threshold`，再调用已有的通用 `build()`。当阈值为 1、传入 4 时，权重已经加载，服务却在 capture 阶段因断言停住，尚未执行正式请求。

补丁给子类 capture 入口加了一条分支。指定候选启用 Breakable Graph 且 query 超过阈值时，直接调用原有的 `self.build(0, metadata)`，让这段 attention 使用 prefill metadata 并在 eager 段运行。参数 0 表示公共前缀长度。这个分支读取真实的 Q4 长度作判断。后续短 query 候选把四行分别展开为因果 Q1，沿用原请求页表并更新每行的可见长度，那时后端 metadata 中的 1 才表示展开后的布局。去 padding 时补传 `seq_lens_cpu_upper_bound` 是另一处字段修复。

<h3 id="pp-feedback-thread-boundary">反馈经过哪个线程才出错？</h3>

以接受 `a,b`、拒绝 `c` 的同一轮为例。末级在设备上把反馈写到 `packed`。它有四个输出槽、三个新草稿槽，另有最后有效输出、有效计数和源位置。末级把数据异步拷到 pinned CPU buffer 并记录 `ready`，前级也分配同形状的 CPU 接收区和设备目标。

1. 两侧 RPC 线程把交换任务提交给各自的后台线程。发送方等 `ready`，让 CPU 中转区可以读取。
2. Gloo 先广播五个整数 `[2, sequence, num_rows, k, identity]`。Header 核对的是格式、轮次、行数、深度和身份。比如前级等第 17 轮，收到第 16 轮就报错。正文随后才广播到 CPU buffer。
3. 前级在指定设备和反馈 stream 上提交 `packed.copy_(cpu, non_blocking=True)` 并记录完成 event。Future 可以先返回 event。消费 stream 等 event 后才能读取反馈，buffer 的引用也要保留到相关操作完成。

最早的 `_submit()` 直接把原函数交给线程池。RPC 线程创建的 inference tensor 可以跨线程传递，PyTorch 的 `inference_mode` 开关留在原执行线程。后台任务在模式关闭时原地修改 inference tensor，会触发异常并中断请求。`no_grad()` 关的是梯度记录。实验记录只把首条 API 的失败定位到后台反馈路径，具体第一个抛错算子仍未知。接收侧的 `copy_` 是源码可见的一个原地写入点。 [PyTorch 原地更新检查](https://github.com/pytorch/pytorch/blob/main/c10/core/TensorImpl.h#L2962)

```python
# _submit：在线程池实际执行的函数内部进入推理模式
def run():
    with self.torch.inference_mode():
        return fn(*args)

future = self.pool.submit(run)
```

交换和经同一入口提交的回调都获得了正确的 PyTorch 模式。操作系统的运行、就绪和阻塞描述线程是否能获得 CPU。推理模式描述这个线程执行 PyTorch 运算时使用的开关。设备和 stream 的选择，以及 Future 返回后还要等哪个 event，分别由反馈代码管理。

### 从现象开始定位，而不是从补丁开始

| 出现阶段 | 现象与区分实验 | 修改 |
| --- | --- | --- |
| 真实权重初始化 | 非末 PP rank 访问了仅末级创建的 drafter | 将加载、backend 初始化、dummy、capture 等使用点对齐到末级所有权。各阶段仍捕获所需的目标特征 |
| Q4 warmup / capture | MLA capture builder 原先按 Q1 解释输入 | 为指定 Q>1 路径提供匹配的 metadata，按候选的 Graph 策略保留 attention eager 段 |
| Native 预检 | Q4 展开后超过 Q1 单次容量，宽表空槽和 padding 要区分 | 按 native 容量分块，保留逐 query 精确因果端点，覆盖空槽和不同请求布局 |
| 第一次 API | 主线程正常，后台 transport 访问 tensor 时模式不匹配 | 在线程池入口包裹 `inference_mode`，再走真实传输与回调 |
| KDA prefill | 某些缓存起点下，长 prefill 的前 3 个卷积输出错误，已测后续输出和最终卷积缓存正常 | 保存原历史与输入，用私有 Q1 状态重算前三个位置 |
| Native 状态索引 | `block_table[:,0]` 值正确，列视图 stride 可能为 4 | 使用连续索引，并检查 dtype、shape、stride 与有效槽 |
| 投机 decode | 拒绝后缀有可能被带入下一轮递推 | 验证每个接受边界，按反馈发布本地状态，在消费或复用前等对应 event |

卷积的前缀现象可以用宽度 4 的小例子理解。已有历史 `[a,b,c]`，新输入 `[d,e,f,g]`。前四个窗口依次为 `[a,b,c,d]`、`[b,c,d,e]`、`[c,d,e,f]`、`[d,e,f,g]`。前三个窗口依赖旧缓存，第四个开始全是新输入。最终卷积缓存正确也无法补回已经进入递推的错误输出。后来的精确路径分开线性卷积和 SiLU，使用 FP32 scratch，按实际请求长度发布普通历史并保留投机列。分块 prefill 要将同一请求前一块的最终状态交给下一块。

旧历史指上一段最后的三个输入值，旧缓存是这个请求的 `conv_state` 槽里存这些值的位置。把它们写成 `[1,2,3]`，新输入写成 `[4,5,6,7,8]`，将卷积简化成窗口求和：

| 当前输入 | 正常输出 | 模拟旧历史被当作 0 时的输出 |
| --- | ---: | ---: |
| 4 | 10 | 4 |
| 5 | 14 | 9 |
| 6 | 18 | 15 |
| 7 | 22 | 22 |
| 8 | 26 | 26 |

两边最后的卷积缓存都是 `[6,7,8]`。最终缓存存的是最近三个输入，因此会覆盖旧历史。置零是图中的演示假设。项目定位到的是 native 批量卷积接续旧缓存时前三个输出错误，现有证据没有区分内核读错了历史地址、用了错误的值，还是计算时漏掉了历史贡献。修补是在批量卷积覆盖缓存前保存输入和历史，再用私有 Q1 状态重算前三步，替换对应输出。

索引布局故障也有独立的对照。假设块表三行第一列是 `[7,21,35]`，每行四列。打印值正常，但它们实际位于底层位置 0、4、8，native 接口拒绝这样的跨步向量。`.contiguous()` 只把槽号复制成紧挨着的布局。索引连续化后，带缓存长 prefill 的前三步仍可复现错误，因此两项分别修、分别验。

验证时先固定输入和初始状态，比较普通 Q1、Q4、串行、并发和重复执行。找到首个分歧位置，再对投影、卷积、激活、递推输出、最终状态、全状态池和 NULL 页逐层检查。参考实现也可能有问题，早期出现过参考 g 维度不对和索引 stride 不满足 native ABI，修复参考后才重新比较。固定题通过、组件逐字节通过和整模逐 token 通过各有自己的覆盖范围。

### 如何把瓶颈分析变成一组能回答问题的实验

1. **先冻结对照。** 对齐 checkpoint、服务源码和启动参数，固定 C32、请求体、1024 输入和 1024 输出、缓存准备与质量口径。分别保留历史 XLSX、同期控制组与候选结果。每轮记录成功数、TTFT、TPOT 和输出 TPS。启动成功、固定答案和严格 token 对照分别验收。
2. **拆开时间线。** 在每个 PP stage 记录调度、输入准备、前向、发送、反馈到达、状态发布和下一次消费。区分 host 排队、设备算子和通信，按同一批次对齐 rank。一个 rank 很晚才发起通信，需要先看它之前等待什么。聚合完成窗口时取同主机最早开始到最晚完成，避免把错峰遗漏掉。
3. **先查执行栈是否变了。** 早期 EAGLE3 同时改变同步/异步、预算和 Graph。调度器回放发现相关同步路径会把 32 拆成 16+16。相同 32 有效 token 的 MoE 组件单批约 1.033 ms、两批约 1.553 ms、三批约 2.011 ms。先恢复 V1 异步、预算和原 Graph 路径，再看投机净收益。slot mapping 缓存复用不变的设备常量，组件成本约 58.50→16.31 μs。
4. **沿等待边找真实资源依赖。** 两个独立请求可能同时带 NULL0，旧 fence 按块交集等待。用真实 allocator 与受控延迟 Future 对照仅 NULL 相交、真实块相交。过滤非正块 ID 后，仅保留真实资源依赖，并验证 group、抢占、复用和过期反馈。合成 TP8/PP3 流水线约 2.54 倍是该组件对照，对应整模阶段为 239.12/243.64 tok/s。
5. **精确化与 Graph 分开评估。** 精确 KDA prefill 某个 16K body 从约 26.5 ms 增到 49.8 ms，是以成本换精度的路径。Greedy verifier Graph 的完整 sampler forward 约 2.17→0.56 ms，是另一项组件结果。共享 KDA Graph 还需记录真实 worker 命中、冷 capture、并发、stream 和 fallback。r25 实际两轮 247.5310/247.5436 tok/s，A 臂数值门禁失败后没有完成严格配对。
6. **压缩候选成本之前先校验语义。** KDA 快照组件在 C32/Q4 下，保留接受前缀为 0.3936495 ms，final-only 诊断为 0.3878540 ms。约 5.8 μs 的差异不足以支持牺牲状态回滚。MLA 对比要同时保留宽表 Q1、紧凑 Q1、native shared，并从 kernel 扩到完整层和真实布局。端点毒化留下 Q4/Q1 的 59 元素差异，最大绝对差约 3.8147e-6。串行 Q1 通过 10 配置、58 波，但在两个代表性配置中比紧凑旧路径慢约 8.88% 和 11.07%，未进入最终版本。
7. **用整轮成本决定投机深度。** 每轮有效输出量除以完整循环时间才对应收益。按历史 D3 存活率做条件推导，D2 需要将完整循环降时约 11.9% 才能持平。只有实际 query、状态和反馈成本随深度下降，局部 kernel 的节省才可能兑现。DSpark P4/P6 处于组件与配置资格阶段，无法继承原 R6 成绩。
8. **回到正式负载。** 恢复后的原 R6/EAGLE3 D3 在 C32、160 个 1024→1024 请求上输出 163840 tokens，用时 650.298010 s，得 251.9460 tok/s。相对指定历史 XLSX 207.01 tok/s 提升 21.71%，均值 TTFT 10.43963→3.95830 s，TPOT 144.47→116.34571 ms。160/160 成功，固定题 44/44。共享子 Graph、native MLA 与串行 Q1 未纳入这轮；后续严格数值诊断仍有反例。组件收益不能直接相加为该整模提升。

### 提问、作答与复盘

在复盘里我曾把末级反馈理解成「draft 已经输出了，接着给下一轮准备验证的输入」。这个说法抓到了新候选是下一轮输入的一部分，遗漏了反馈中还带有**本轮已提交输出**与**供各阶段校正进度的计数和位置**。更准确的口述是「本轮 target 先验证旧候选并提交输出，末级再产生新候选，一起反馈。本轮最后有效输出与新候选组成下一轮 Q4」。

下面的问题来自这次讨论与能核对的侧边提问。右列给的是复盘答案，用于回看时自测。

| 我问过的问题 | 能把因果讲清的答法 |
| --- | --- |
| FP16 激活到底是什么？ | 当前请求计算产生的特征。INT4 描述被量化专家的权重，FP16 描述主路径激活，累加和持久状态要另外看。 |
| 三节点 TP8/PP3 是怎么接的？ | 各节点八卡分摊同一段层内张量，三段依次完成目标前向。完整 draft 在末级本地 TP8，辅助特征由前两级沿前向带过去。 |
| 接受 token 数不同，Graph 怎么处理不同矩阵？ | 有效输出数通过计数和索引表达，完整 D3 下一轮仍是 Q4。批量几何变化时换桶或回退，命中固定形状时更新稳定 buffer 中的内容。 |
| 调度器是什么，为什么不先拿所有 token？ | CPU Scheduler 选请求、工作量与缓存资源，worker 真正消费时按反馈恢复候选。CPU 随后仍处理提交结果。 |
| MLA builder 与 metadata 有什么关系？ | builder 是转换代码，metadata 是输出的数据。将通用的请求边界、长度、页表组织成特定后端的输入。 |
| CPU 长度上界是什么？ | 按上一轮全接受估算的长度，可供 host 规划。精确长度用于真实的历史访问。 |
| 反馈和 metadata 有什么关系？ | 反馈提供上一轮结果、有效数量和位置，worker 再结合本轮调度与缓存管理构造算子所需的数据。 |
| inference_mode 的上下文、RPC、transport、线程池是什么意思？ | RPC 发起 worker 调用，transport 交接反馈，线程池运行后台任务。推理模式属于执行任务的那个线程。 |
| KDA prefill/decode 有什么现象，能否先举例？ | cached prefill 前三次卷积仍依赖旧历史，缺陷在这些位置出现。投机 decode 则按接受前缀恢复状态。用卷积窗口与拒绝 c 的两轮例子分别说明。 |
| Q4 需要改哪个字段？capture 入口和 build 是什么关系？ | Runner 算出 max_query_len=4，补丁读它分流到已有 build。后续把 Q4 展开为 Q1 时，才按新的后端布局填 1。 |
| query_start_loc 包含历史吗？ | 写出 [0,4,5]，解释它只给本轮行编号。再单独说 A 的 seq_len=104 与历史长度 100。 |
| 原地更新检查只是额外开销吗？buffer 和 header 又是什么？ | 检查失败会中断请求。CPU buffer 存反馈正文，header 核对批次，event 管设备依赖。模式在后台任务内部开启。 |
| 为什么最终缓存正常，前三个输出仍然会错？内核究竟哪里错了？ | 画出依赖 3、2、1 个历史值的三个窗口，再说明最终缓存保存新输入。能定位到批量卷积接续路径，具体内核缺陷仍未知。 |

还有三道复述练习适合检验有没有把证据讲过头。**44/44 固定题说明了什么？** 只说明该小集通过。**为什么没有将 native MLA 的核心倍率写进最终成绩？** 最终版本归属不同，且严格对照与完整入口成本仍有门槛。**为什么不用三台平均卡利用率直接决定迁层？** 活动率混合了计算、传输和等待，先按 rank 时间线确定最慢阶段与等待来源，才有条件评估层划分。

## 十二、这次排查留下的几条判断习惯

对我而言，最有用的变化是把几个经常混在一起的概念拆开：

- socket 是物理 CPU；NUMA 是 CPU/内存访问域，两者数量不必相同。
- 主机 RAM 与 P800 显存分别计量，`MemTotal` 也不等于空闲容量。
- XL/PIX/SYS 描述拓扑条件，真实集体通信选路需要运行证据。
- GPU 活动率包含不同形式的等待，不能直接用于分层。
- 接收调用的等待时间与裸数据传输时间要分别测。
- 更低 TTFT 与更高输出吞吐是不同目标，必须分别验收。
- 能够指出“哪个批次、哪个 rank、在哪条依赖上卡住”，才有足够依据选择下一项优化。

本文的工程依据包括原瓶颈报告、模型配置与分层记录、实际安装包 P1 验证、decode 时间线、调度单波对照，以及三机硬件核查。单波收益、部分设备采样和未确认的交换机布线，都保留了它们的证据边界。
